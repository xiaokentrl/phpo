# 状态同步

> 对应 AGENTS.md §1.8 / §5.6 / §5.6.2 / §5.6.3 / §0.2-10（禁止状态不同步）/ §0.2-29（禁止事件到了界面却因单个字段缺席而不动）/ 工单 T704。核心原则：**后端唯一权威 + 前端订阅事件**；无本地乐观更新。冲突以 AGENTS.md 为准。

## 1. 权威模型（§0.2-10）

- 后端是唯一权威（single source of truth）；前端只订阅事件、渲染快照，**不做乐观更新**（硬红线 4）。
- 快照 `model.Snapshot` 是权威态的完整物化（§领域模型 4）：`installed` / `running` / `sites` / `env` / `phpExtensions` / `dirReady` / `tasks`。**形状契约**：其中的切片/映射字段在线上一律为 `[]` / `{}`，不得为 `null`（见 §4.5）。
- 持久形态两处：运行态在 SQLite（`internal/store/`），配置真相在 `config.yaml`（`internal/config/ConfigStore`）。`store/snapshot.go#BuildSnapshot` 从状态表物化运行态，并由注入的 `EnvProvider` 合成 `env`、派生 `dirReady`（两根已持久化 + 目录存在性，不落库）。
- `sites` 的展示用运行态 `health` / `hosts` 同样**不落库**，在 `BuildSnapshot` 出口由 `enrichSites` 按宿主真值逐站点派生（hosts 走注入的 `HostsProbe`，health 走 `model.SiteRuntime.Health()`）。`BuildSnapshot` 是全部 `state:changed` 广播与 `GetState()` 的唯一快照来源，故此处一处落地即处处一致。
- 首启（两根未写入 `config.yaml`）时 `BuildSnapshot` 直接返回空运行态且不建库；两根落地后首次访问透明「建目录 → 建库 → 迁移」。

## 2. 写 → 落地 → 广播（三段式回流）

```
UI 动作 → preflight（唯一裁决）
        → task.Manager 三段式（Pre-Clean → Execute → Post-Verify）
        → applyStateChange（写库，如 store.UpsertSite / SetRunning）
        → emit("state:changed", { snapshot })   # 后端拉取权威快照后广播
        → 前端 useStateSync 写 appState store → 视图重绘
```

`SiteService.emit()` / `AppService` 各写操作落地后统一 `Emit("state:changed", {snapshot})`（`site_service.go:278`、`app_service.go`）。事件名全表见 [事件流协议](./事件流协议.md)。

## 3. 校准：Docker ≡ SQLite（一致性）

- `engine/calibrate.go`：拉取 Docker 实际态 ⇄ SQLite 记录比对；漂移 → `docker:state-drift { expected, actual }`，可 `App.Calibrate` 修正。
- 触发时机（§5.13.9）：启动时 + 每次任务后 + 手动。
- `running=false` 反向推导：容器 `State.Running` 不等于服务进程就绪（entrypoint 前置脚本），健康门控不只看 Running（见 project 记忆「container readiness race」；实现见 `engine/health.go`）。

## 4. 前端订阅（唯一通道）

- `composables/useStateSync.ts`：注册全部 17 协议事件订阅（`api/events.ts#ALL_EVENTS`），把权威态写入 Pinia `appState` store。
- 组件只读 `appState`，**不各自订阅**、不本地改写（§界面规格 8）。
- 刷新/断线兜底：`App.GetState()` 拉全量快照对齐（`app_service.go#GetState`，见 [接口契约](./接口契约.md) §2）。

### 4.1 事件通道实现（Wails v3）

`api/events.ts#onEvent` 用 `@wailsio/runtime` 的 `Events.On(name, (ev) => handler(ev.data))` 订阅，并返回反订阅函数。

> **踩过的坑**：Wails v3 **没有** v2 的 `window.runtime` 全局。若按 v2 写法 `window.runtime.EventsOn(...)`，探测结果为 `undefined`，回调被静默丢弃且不报错——17 个协议事件与 `ui:command` 全部失效，表现为「点了按钮界面不动」。宿主可用性一律按 v3 口径探测，且**判据只能取宿主独有字段** `window._wails.flags` / `.environment`（由 `wails/v3/internal/runtime.Core()` 注入，见 `api/site.ts#hasBackend`）。**`window._wails.invoke` 不是宿主信号**——`@wailsio/runtime` 自己在任何 DOM 里都会挂它（`dist/index.js`），纯 Vite 浏览器同样为真；曾把它计入判据，结果浏览器预览被误判成「有后端」：占位数据永不出现、界面显示「环境为空」、装机向导在无人应答的调用上抛错，每个绑定调用都打向不存在的 `/wails/runtime`（404 风暴）。纯 Vite 浏览器（真无宿主）另接模块内本地事件总线，只为 demo 回放。

### 4.2 写后收口：事件 + 主动拉取双保险

事件推送是异步的，且后端某些写路径（如 `EnvService.SetPort`）只广播而不产生任务日志，单靠订阅会出现「后端已改、界面未动」的时间窗。因此：

- **快照内数据**（`installed` / `running` / `sites` / `env` / `phpExtensions` / `dirReady` / `tasks`）：所有写操作统一在 `composables/useTask.ts#submitWrite` 或各模态的 `finally` 段 `await` 后端调用后调 `syncState()`（`useStateSync.ts`，取一次 `GetState` 走同一 `applySnapshot`）。**成功时以快照为准、失败时同样以快照为准**（后端已回滚的中间态不会残留界面）。真实宿主下 `runTask` 只登记任务参数（界面不再外显等效命令，AGENTS.md §1.4）并展开抽屉，不改任何状态。`env` 除端口/密码外还含三个可自定义根键 `OFFLINE_ROOT` / `BACKUP_ROOT` / `{KIND}_{VER}_DATA_DIR`（`applySnapshot` 先清后 assign，不会残留旧根）——改根的界面回显只认这些键，输入框不回填本地值。
- **快照外数据**（备份列表 `BackupList`、离线缓存 `ListCacheEntries`、回收站与审计 `ListOperations`、doctor 报告、原生配置正文 `ConfigGetFiles`）：不在 `Snapshot` 内，事件再全也不会刷新它们，必须在对应写操作后**显式重拉**（`useCache.ts` / `useCleanup.ts` / `BackupView` 各自的 `load*()`）。漏拉即界面停在旧记录。
- **UI 偏好例外**：主题、布局、缩放、语言、托盘开关属前端偏好（§3.1 原则 5），走 `localStorage`（`stores/prefsStore.ts` / `layoutStore.ts`），不进快照、不等后端广播——但必须持久化，否则重启回弹等于「点击无效」。托盘偏好的**下发失败必须可见**：`prefsStore.mirrorTray()` 的 `setTrayPrefs` 一旦 reject 就弹 `settings.tray.pushFailed`，因为勾选已写进 `localStorage` 并显示为「已生效」，原生托盘却没变＝界面失真（与硬红线 4 同一口径）。无宿主时 `api/state.ts#setTrayPrefs` 直接跳过，demo 下不会误弹。

### 4.3 首帧：真实宿主不得残留占位假数据

- `stores/appState.ts` 里的原型占位数据（`installed` / `sites` / `backups` / `offline` / `phpExtensions` / `env` 的端口密码）**只在无宿主（纯 Vite demo）下铺**，判据是 `demo = !hasBackend()`；真宿主一律从空开始，等 `GetState` / `state:changed` 落地。
- 宿主 Core 可能**晚于** store 建立才注入，`hasBackend()` 在 store 实例化那一刻可能还是 `false`。故 `App.vue` 在 `await waitForBackend()` 之后、`startStateSync()` / `syncState()` 之前调一次 `app.enterRealHost()` 收掉可能已铺下的占位数据（含 `dirReady` 两项回落 `false`，由权威快照重判）。**顺序不能颠倒**：先拉快照再收，会把真宿主的真实数据一起抹掉。
- 真宿主下 `env` 只保留 `derivePaths` 的路径兜底键。后端只发 `{KIND}_{VER}_PORT` / `{KIND}_{VER}_PASSWORD`（`internal/config/configstore.go` 的 `EnvKey*`），`applySnapshot` 也只清这些键——再种 `NGINX_PORT` / `NGINX_VERSION` / `*_ROOT_PASSWORD` 这类原型遗留键，等于往快照里留下一辈子没人覆盖的假值。
- 同一口径的镜像修正：`usePreflight` 的 `offline-prune` 预校验在真宿主下查 `cacheStore.entries`（后端 `ListCacheEntries` 权威），不再查恒为空的 `app.offline`，否则每个真实缓存条目都会被报成「缓存条目不存在」。

### 4.4 系统日志通道：无任务时事件也要看得见（需求 3/6）

「后端已发、界面无声」是同一类缺陷的另一半：`cache:*` / `docker:*` / `update:*` 事件在**没有运行任务**时曾无处呈现（离线缓存页的 `.off-events` 只是本地列表，已删除）。现由 `taskStore` 的系统日志通道承接：

- **入口唯一**：`eventLine(level, text)`——`app.tasks.running?.id` 有值则 `appendLog` 归入该任务，否则 push 进 `sysLines`。调用方只有 `useStateSync.ts#eventNote` 一个，不存在第二条写日志的路径。
- **不是任务**：`sysLines` 不建 `TaskBrief`、不进 `Snapshot.Tasks`、不落 `operations` 账本，抽屉右栏也不会因此多出一行——**后端任务状态仍是 4 个、事件名仍是 17 个**（硬红线 4、§0.3）。
- **有上界**：`SYS_MAX = 200`，超限裁头部（保留最近 200 行），防长跑进程无界增长（AGENTS.md R92）。
- **空态有文案**：无任务且无系统日志时显示 `task.sysEmpty`，不留空白区。
- **豁免一项**：`update:progress` 不进日志（连续量，已由升级弹窗进度条承载）。其余事件逐行落地，见 AGENTS.md §5.6.2 的 17 行对照表。

### 4.5 快照形状契约：一条落地链不得被单个字段打断（AGENTS.md §5.6.3 / v2.9.12）

`state:changed` 到界面不是一次赋值，而是**一条链**：`store.BuildSnapshot` → `Emit("state:changed")` → `useStateSync.landEvent` → `appState.applySnapshot` → `applyTaskBoard` → `taskStore.syncBoard` → 抽屉右栏。**链上任一处抛错即整链中断**——事件确实收到了，界面却一动不动；而中断点若落在一个「与本条数据显示无关」的字段上，缺陷会伪装成「后端没推」。

真机现象：点 PHP 的启用/停用，抽屉队列行显示 `start-2` / `stop-1`，**必须手动刷新页面**才看到「启动 phpo-php-8.0 已完成」。因果是：零站点库里 `snap.Sites` 为 nil → JSON `"sites":null` → `applySnapshot` 展开 `s.sites` 抛 `TypeError: s.sites is not iterable` → 同函数末尾的 `applyTaskBoard` / `syncBoard` **永不执行**，队列详情（含人话标签）一起丢掉；早到一步的 `task:log` 已用任务 ID 建了占位行，界面就停在 ID 上。刷新后之所以正常，是因为走了另一条路（`loadHistory()` 读任务账本 `op.label`）——这恰好证明**实时链路是断的**，只有事后链路活着。同一抛错还让 `syncState()` 失败，影响面不止队列。

三条契约（对应 AGENTS.md §0.2-29、R98）：

| # | 契约 | 落点 |
|---|------|------|
| 1 | 可空集合必须序列化为 `[]` / `{}`，不得把 `null` 交给前端（零站点、无排队项两条都会命中） | `internal/store/snapshot.go` 的 `normalizeCollections`，在 `BuildSnapshot` 两个 return 前各调一次；用例 `TestBuildSnapshot_NoNullCollections` 反射遍历快照的切片/映射字段（含嵌套 `tasks.pending`） |
| 2 | 前端逐字段兜空（`?? []` / `?? {}`）。**兜空不是乐观更新**——值仍只来自快照（硬红线 4） | `appState.applySnapshot`（`sites` / `phpExtensions`）、`applyTaskBoard`（`running` / `pending`）、`taskStore.syncBoard` |
| 3 | 不得用 try/catch 吞抛错来代替修契约：藏起异常等于把「事件发了界面却不动」永久化 | `useStateSync.ts#landEvent` 不加兜底捕获 |

**验收口径**：队列行标签的唯一来源是权威快照里的 `TaskBrief.Label`（人话文本），且必须在**任务开始那一帧** `state:changed` 就落地——不得以任务 ID 示人，**不得把「刷新后就正常」当验收通过**（本产品要求不刷新也对）。`task:log` 早于快照到达时可暂以 ID 占位（跨事件顺序不保证），但同一帧快照落地即须覆盖成人话标签。

## 5. 停止态与「stopped 反向推导」

原型 `stopped` 由「已安装 ∧ 非运行」反向推导，生产在快照构建处统一物化（`BuildSnapshot`），前端不自行推导状态，避免与后端漂移。

## 6. 任务队列与任务账本（实时可见）

装/停/启/卸载/建站/改配置/备份/清理等**一切写操作都在 `task.Manager` 里跑**，因此每一条写操作天然有队列位、进度、终态与失败原因，无需前端自造。

- **队列详情不落库、随快照推送**：`model.TaskBoard{ Running *TaskBrief, Pending []TaskBrief }` 挂在 `Snapshot.Tasks`，由 `Manager.SetQueueWatcher` 在入队/出队/移交时触发重发 `state:changed`。排队态由「落在 `pending` 分区」表达，**不新增第 5 个任务状态**（§0.3 冻结 4 个），也**不开第 18 个事件名**（§5.6 冻结）。
- **行标签取自 `TaskBrief.Label`，在开始那一帧即落地**：抽屉右栏每行显示的人话文本（「启动 phpo-php-8.0」「删除站点 demo.test」）唯一来源是权威快照的 `Label`，由 `taskStore.ensureLive` 在 `syncBoard` 时覆盖早到 `task:log` 留下的 ID 占位。后端侧由 `internal/app/queue_events_test.go` 锁死「任务一进入运行态即推出带 Label 的 `state:changed`」；前端侧由 §4.5 的形状契约保证这一帧走得完。
- **串行 FIFO**：`Manager.acquire` 单飞，一次只跑一个任务；同 `label` 重复提交返回 `ErrQueued`，任务内嵌套提交返回 `ErrBusy`。二者都是后端当场拒绝，前端 Toast 上抛、不改本地状态。
- **进度实时**：每个 step 完成 `emit task:progress{id,step,total}` + 人话 `task:log`；`step/total` 同时回写 `TaskBrief`，使抽屉首帧（快照）与后续事件一致。
- **队列详情可定位到被操作对象**：`TaskBrief` 的 `kind` / `version` / `domain` 来自 `model.TaskMeta`（`briefOf` 逐字透传），服务卡片据此把「执行中 {step}/{total}」「等待中」标在**被操作的那一版**上，站点行据 `domain` 标在**被操作的那个站点**上。前端不从 `label` 文案反推——文案随 i18n 变化，反推等于把 UI 同步挂在翻译上。指示只增不改：卡片/站点行的状态点与排队标记对所有任务照常铺开，其他按钮照常可点（并发写按 FIFO 排队，§5.6）；**唯一禁用的是用户点下的那一颗**，等待期 `:disabled="tasks.isBusy({...})"`，到本次操作收口并 `await syncState()` 之后复能（AGENTS.md §5.6.4）。
- **抽屉的显示态是派生量，不是后端状态**：`taskStore.ts#displayOf` 把「权威快照分区 + `task:done` 终态」映射成 UI 六档——`waiting`（等待中）/ `running`（执行中）/ `done`（已完成）/ `failed` / `cancelled` / `unknown`（预留兜底）。后端 `model.TaskStatus` **仍是 4 个**、事件**仍是 17 个**；新增显示态只改 `displayOf` 与 `DISPLAY_LABEL`，不动 model。
- **一经入队就在列表里**：`syncBoard` 为 `Running` **和每一个 `Pending` 项**建/更新记录（排队项无日志，左栏空态提示），行位**只随提交先后**决定（记录池 newest-first，运行中任务不因取得执行权而下移）。撤回成功的行随下一次快照消失；若被撤回项正被选中，选中在同一次快照里回落到运行中任务，不留「状态未知」的幽灵详情。判定「已撤回」用的是四件同时成立的事实（真实记录 + 仍标执行中 + 零日志 + 不在权威队列），**不是本地乐观删除**。
- **终态与原因**：`task:done{id,status,duration}`（duration 为 Go `time.Duration`，JSON 是**纳秒**）；失败原因取该任务最后一条 `err` 级 `task:log`。
- **任务账本（跨重启可回看）**：`internal/task/ledger.go` 在 `Manager` 出口一处落账，复用 §5.13.10 的 `operations` 表，迁移 `0008_add_task_ledger.sql` 加 `task_id / label / logs` 三列；`logs` 只保留**尾部 500 行**（`maxLedgerLines`），防长任务无界增长。前端 `api/task.ts#listTaskHistory` 过滤带 `taskId` 的行渲染「历史任务」。
- **首启零落盘不破**：账本写入走运行态 store，两根未就绪时任务本身已被 `ErrHomeNotSet` 拦住，不会提前建库。

## 7. 禁止清单（§0.2）

- ❌ 前端改完本地状态直接显示成功（乐观更新）。
- ❌ 绕过 `state:changed`，靠轮询/WebSocket 拉状态（Wails Events 已足够，§2.1）。
- ❌ 写操作不广播即返回（必须 `applyStateChange → emit`）。
- ❌ Docker 与 SQLite 长期漂移而不校准。
- ❌ 发事件却没有任何落地处（17 个事件名逐个必须有 store 落地或日志行，见 AGENTS.md §5.6.2 / §0.2-25）。
- ❌ 为了「让事件可见」把非任务事件伪装成一条任务记录，或给 `sysLines` 加上限不设防的无界增长。
- ❌ 快照出口把任何切片/映射字段发成 `null`（新增字段时在 `model.NewSnapshot()` 或 `normalizeCollections` 里给空集合）。
- ❌ 在前端「包一层 try/catch 让它别抛」来代替修形状契约（§4.5）。
- ❌ 队列行显示任务 ID 当标签，或用「手动刷新页面后就正常了」当作实时同步的验收通过（§4.5）。
