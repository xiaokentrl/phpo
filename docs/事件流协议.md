# 事件流协议

> 对应 AGENTS.md §5.6（事件协议）/ §0.2-10（状态同步后端唯一权威）/ §5.6.3（快照形状契约）/ §0.2-29（禁止事件到了界面却不动）/ §3.2（前后端通信）/ 工单 T704。事件名与载荷以本文表为准；后端发射器 `internal/app/emitter.go`，前端唯一订阅通道 `frontend/src/api/events.ts` + `composables/useStateSync.ts`。冲突以 AGENTS.md 为准。

## 1. 通信模型

- **单向权威**：所有状态由后端计算 → 发射事件 → 前端订阅回流。前端**从不本地乐观更新**（硬红线 4）。
- **通道**：Wails 3 Event（`application.App.Event.Emit`）。`app.go` 的 `wailsEmitter` 是 `internal/app.Emitter` 到 Wails 事件系统的适配；未注入 Wails 实例时 `Emit` 静默丢弃（测试/启动早期）。
- **计数**：协议事件共 **17** 个（`ALL_EVENTS` 对账须恰为 17）。另有 `ui:command` 为**前端 UI→UI 本地广播**（托盘/命令面板触发，不经后端），不在这 17 之内。

## 2. 事件全表（§5.6）

### 2.1 状态类

| 事件 | 载荷 | 时机 |
|------|------|------|
| `state:changed` | `{ snapshot }` | 后端状态变化后（任何写操作落地的最终回流） |
| `service:changed` | `{ kind, version, running }` | 单服务运行态变化 |

> **`snapshot` 的形状契约：可空集合为 `[]` / `{}`，不得为 `null`**（AGENTS.md §5.6.3 / §0.2-29）。`state:changed` 在前端是一条落地链（`applySnapshot` → `applyTaskBoard` → `taskStore.syncBoard`），链上任一抛错即**整链中断**：事件到了、界面却一动不动。零站点时 `sites` 为 nil、无排队项时 `tasks.pending` 为 nil，两条都会在 `BuildSnapshot` 出口由 `normalizeCollections` 归一成空集合；前端再逐字段兜空（`?? []` / `?? {}`，仍只认快照值，不是乐观更新）。**不得**用 try/catch 吞掉抛错来代替修契约。
>
> **队列行的人话标签随开始那一帧回流**：`Snapshot.Tasks.running.label`（`TaskBrief.Label`，如「启动 phpo-php-8.0」）是抽屉队列行文本的唯一来源。`task:log` 可能早于快照到达并以任务 ID 建占位行（跨事件顺序不保证），同一帧快照落地即须覆盖成人话标签——**不得**停留在 `start-2` / `stop-1`，**不得**要求用户手动刷新（刷新后走的是账本 `loadHistory()` 这条事后链路，不能当作验收通过）。
>
> **同一个 Label 也是左栏的标题**（AGENTS.md §5.6.4）：队列行文本之外，`TaskBrief.Label` 还要显示在**左栏日志之上**的 `.drawer-task-title`（选中哪件事就显示哪件事的名字；无选中任务即整条不渲染，头部 `.drawer-left` 仍恒为「服务」二字）。事件回流后界面的两项反馈是「名字看得见」+「被点那颗按钮暂时禁用」，后者不是事件、不落状态——它是 `taskStore.inflight` 计数的按钮反馈，不建任务记录、不改后端状态、不落账本（硬红线 4）。

### 2.2 任务类

| 事件 | 载荷 | 时机 |
|------|------|------|
| `task:log` | `{ id, level, text }` | 任务输出一行（`level` ∈ 5 类，见 §领域模型） |
| `task:progress` | `{ id, step, total }` | 步骤进度变化 |
| `task:done` | `{ id, status, duration }` | 任务结束（`status` ∈ running/success/failed/cancelled） |

> **队列详情不开第 18 个事件**：任务队列（运行中 + 其后 FIFO 排队项）以 `Snapshot.Tasks`（`model.TaskBoard{ running, pending }`）随 `state:changed` 推送，前端不轮询、不推断（硬红线 4）。排队态是**结构**（落在 `pending` 分区）而非第 5 个任务状态（§0.3 任务状态冻结为 4）。撤回排队项走 `App.CancelQueued(id)` 写请求，终态仍等后端事件。
>
> **队列的呈现约定（AGENTS.md §5.6.1）**：抽屉右栏（**默认** 30%，与左栏可左右拖拽，40–80 夹取）竖排队列**新提交永远在最上面**（行位只随提交先后决定，运行中任务不因取得执行权而下移）；`Manager.SetQueueWatcher` 在**入队 / 移交 / 撤回**三处重发快照，故任务一经入队即出现在列表，不等执行权。每行的文字状态由 `taskStore.ts#displayOf` 从「快照分区 + `task:done` 终态」**派生**（等待中 / 执行中 / 已完成 / 失败 / 已取消 / 状态未知兜底），事件侧**不新增事件名**、状态侧**不新增第 5 态**；日后加显示档只改前端映射表。
>
> **`duration` 单位是纳秒**：Go `time.Duration` 直接 JSON 序列化，前端按 ns 格式化（`1234567890` → 「完成 · 1.2s」）。
>
> **失败原因有两个来源**：实时侧取该任务最后一条 `level=err` 的 `task:log` 文本；历史侧取 `operations.error` + `operations.logs`（任务账本，见 [状态同步](./状态同步.md) §6）。`task:done` 载荷本身不带原因字段，§5.6 表已冻结，不加键。

### 2.3 升级类

| 事件 | 载荷 | 时机 |
|------|------|------|
| `update:available` | `{ version, changelog, size }` | 发现新版本 |
| `update:progress` | `{ stage, percent, speed }` | 升级进度（stage：download/verify/install） |
| `update:done` | `{ status, version }` | 升级完成 |

### 2.4 Docker 清洁类

| 事件 | 载荷 | 时机 |
|------|------|------|
| `docker:cleanup` | `{ stage, resource, action }` | 清理进度 |
| `docker:orphan-found` | `{ resources: []Resource }` | 孤儿扫描发现 |
| `docker:state-drift` | `{ expected, actual, gaps }`（`gaps: []ServiceGap{kind,version,reason,ref}`，`reason` ∈ `container`/`image`/`extensions_image`；v2.9.14 补，总纲 §5.19.3） | 校准检测到漂移或缺失态 |

### 2.5 离线缓存类（§5.14.11）

| 事件 | 载荷 | 时机 |
|------|------|------|
| `cache:hit` | `{ kind, version, source, size }` | 命中缓存（零网络） |
| `cache:miss` | `{ kind, version, action }` | 未命中缓存；`action` 取 `local`（本机 Docker 已有镜像，零网络就地 save）/ `pull`（需联网拉取）/ `download`（扩展下载编译） |
| `cache:promote` | `{ kind, version, entries }` | 提升到缓存 |
| `cache:corrupted` | `{ kind, version, entry }` | SHA256 校验失败 |
| `cache:cleanup` | `{ mode, freed_bytes }` | 缓存清理完成 |
| `cache:tempdir-cleared` | `{ path, reason }` | 临时目录已清空（4 个必清时机，§5.14.4） |

> 载荷 JSON 标签以后端 `internal/model/` 事件结构体为准（见 [领域模型](./领域模型.md)）；`cache:cleanup` 用 `freed_bytes`，`cache:tempdir-cleared` 的 `reason` 取值为 `compile_success` / `compile_failed` / `cancelled` / `startup_scan` 等语义串。

### 2.6 17 事件的落地处（AGENTS.md §5.6.2，需求 6）

「实时同步」在本项目是**可核对的清单**。17 个事件名逐个有唯一落地处，逐行对照表以 **AGENTS.md §5.6.2** 为准（本文不复制该表，避免两处漂移），此处只记前端机制：

- **唯一分发点**：`composables/useStateSync.ts`。每个事件先经 `landEvent`（改 store / 快照），末尾 fall-through 到 `eventNote`（进抽屉日志），**不存在第二个订阅者**。
- **日志归属**：`taskStore.eventLine(level, text)` 按 `app.tasks.running?.id` 分流——有运行任务归该任务的日志流，无任务进**系统日志通道** `sysLines`（上限 `SYS_MAX=200`，裁尾）。系统日志**不是任务记录**：不建 `TaskBrief`、不落 `operations` 账本、不新增第 5 个任务状态、不新增事件名。
- **唯一不进日志的事件**：`update:progress`（连续量，已由升级弹窗进度条承载）。其余 16 个均有日志行或由 `task:log` 逐行覆盖。
- **`docker:state-drift` 的 `gaps` 逐条点名**（v2.9.14，总纲 §5.19.5）：`e.gaps` 非空时**一条一行** `meta` 进抽屉左栏（`task.dockerGap`，含 kind / version / 人话原因 / `ref`），并且**不再补那条 `expected → actual` 汇总**——同一次漂移说两遍等于把抽屉当日志复读机；`gaps` 为空才退回汇总行，比对值缺席时退化为 `error` 文本。界面侧的服务卡片缺失 pill 只读快照 `Snapshot.Gaps`（`appState.gapOf`），**不做本地推断**（硬红线 4）；未知 `reason` 由 `GAP_REASON_KEYS` 查不到即原样透出枚举名（兜底位，不留空白）。
- **额外回流**：`docker:state-drift` 除写日志外再 `syncState()` 一次，让校准结果跟着快照回来；`cache:*` 六事件触发 `useCache` 重拉缓存条目（非快照数据，不进 `state:changed`）。
- **事件之外的回流**：所有 `api/*` 写调用必须 `await` 后端并随后 `syncState()`；`root-set`（改根）落 `config.yaml` → `Rebind` → `state:changed`，路径条回显只读快照 `env`，**不回填本地输入框**。

## 3. 典型事件时序

### 3.1 安装服务（缓存未命中）

```
App.Install → preflight OK → task.Pre-Clean
  → ImageExists 探本机镜像库
      ├─ 已有（action=local）→ 零网络 save
      └─ 没有（action=pull） → pull → save
  → verify → 提升 → 清空临时目录
      emit cache:miss{action} → cache:promote → cache:tempdir-cleared
  → 容器装配 → Post-Verify → applyStateChange
      emit task:progress* → service:changed → state:changed → task:done
```

> 未命中分支先探本机 Docker 镜像库（AGENTS.md §5.14.3 v2.9.6 第二优先级）：缓存被误删或换机后，只要镜像还在本机就能零网络把缓存重建出来；探针报错必须上抛，不得静默当作「本机没有」。扩展无此级，未命中即 `action=download` 联网。

### 3.2 安装服务（缓存命中）

```
App.Install → preflight → lookup+SHA256 OK
  emit cache:hit → docker load → 容器装配
  emit service:changed → state:changed → task:done   # 无网络、无 promote
```

### 3.3 取消

```
App.Cancel → manager 触发 context 取消 → 正在跑的 step 感知 ctx.Done
  → 逆序 Rollback（30s 超时）→ 清空临时目录 emit cache:tempdir-cleared(reason=cancelled)
  → emit task:done(status=cancelled)
```

### 3.4 并发提交（串行 FIFO 队列）

`task.Manager` 单飞串行：任何写操作都在自己的任务里跑，第二个不并行执行、也不被拒绝，而是排队。

```
App.Install(php 8.4)  → 任务 A 运行，Snapshot.Tasks.running = A
App.Install(mysql 8.4)→ 任务 B 入队，queue watcher 触发
  emit state:changed{ tasks:{ running:A, pending:[B] } }   # 队列详情随权威快照推送
A 每一步 → emit task:log / task:progress（A 的 id）
A 终态  → emit task:done(A) → B 移交执行 → emit state:changed{ running:B, pending:[] }
```

- **重复提交拒绝**：同 `label` 已在 running/pending 中 → 立即返回 `ErrQueued`，前端以 Toast 上抛，不入队、不产生第二条记录。
- **任务内嵌套提交拒绝**：step 内再调写操作 → `ErrBusy`（排队等于等自己 → 自锁），快速失败。
- 两种拒绝都不落队列、不落账本，属于「后端当场拒绝」，与任务失败（`task:done(failed)`）是两条路。

### 3.5 撤回排队项

```
TaskDrawer「撤回」→ App.CancelQueued(id) → 命中返回 true 并 emit state:changed（该项从 pending 消失）
                                          → 未命中（已移交执行/不存在）返回 false，前端不改本地状态
```

撤回针对**尚未执行**的排队项，无需回滚，因此不发 `task:done`，也不 emit 任何新事件名——后端对未获执行权的任务不发事件、不落账（`internal/task/task.go`），前端队列行随下一次快照消失；若被撤回项正被选中，选中在同一次快照里回落到运行中任务（AGENTS.md §5.6.1）。运行中任务只能 `App.Cancel()`（见 3.3）。

## 4. 前端订阅契约

- `api/events.ts` 导出 `EVENT` 常量（与 `internal/app/emitter.go` 一一对应，**禁止漂移**）与 `ALL_EVENTS` 对账数组。
- `useStateSync.ts` 统一注册订阅，把 `state:changed` 写入 `appState` store，`task:*`/`cache:*`/`update:*` 分派到对应 store；视图只读 store，不各自订阅。
- 断线/刷新后靠 `GetState()` 兜底拉全量（见 [接口契约](./接口契约.md) §2），保证「后端唯一权威」不因前端生命周期丢失。
