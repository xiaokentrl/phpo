# 离线缓存协议

> 对应 AGENTS.md §5.14.10（缓存服务层 API）/ §5.14.11（缓存事件）/ §5.13.13（缓存与清洁协同）/ 工单 T704。本文是缓存子系统对外的**契约**：事件载荷 + 服务层 API + 与 Docker 清洁的边界。冲突以 AGENTS.md 为准。

## 1. 缓存事件（§5.14.11，6 个）

事件名与 §5.6 主表一致，此处给出载荷字段与发射时机（发射器 `internal/cache/manager.go`，后端唯一）：

| 事件 | 载荷 | 发射时机 |
|------|------|---------|
| `cache:hit` | `{ kind, version, source, size }` | 命中且 SHA256 通过（零网络） |
| `cache:miss` | `{ kind, version, action }` | 未命中；`action=local`（本机 Docker 已有镜像，零网络 save）/ `pull`（联网拉取）/ `download`（扩展下载编译） |
| `cache:promote` | `{ kind, version, entries[] }` | 成功后 mv 临时→缓存并登记 manifest |
| `cache:corrupted` | `{ kind, version, entry }` | 校验失败，标记损坏并落入未命中分支 |
| `cache:cleanup` | `{ mode, freed_bytes }` | 三模式清理完成 |
| `cache:tempdir-cleared` | `{ path, reason }` | 四类必清时机各一次（见 [临时目录生命周期](./临时目录生命周期.md)） |

载荷结构体在 `internal/model/cache_entry.go`（`CacheHitEvent` 等）；`source` 标明命中来源目录，`entries` 为 `ManifestPackage[]`。事件均经 `state:changed` 之外独立通道，前端 `cacheStore` + `useCache.ts` 订阅。

## 2. 服务层 API（§5.14.10，`offline_service.go`）

`OfflineService` 接口 12 方法，`app.go` 以 `Offline*` 前缀暴露为绑定：

| 接口方法 | 门面方法 | 语义 |
|---------|---------|------|
| `ListCacheEntries` | `OfflineListEntries` | 遍历条目 + 聚合 manifest 计数/校验态 |
| `GetCacheEntry` | `OfflineGetEntry` | 单条（不存在返回 null） |
| `GetCacheStats` | `OfflineStats` | 根目录总览 |
| `VerifyCacheEntry` / `VerifyAllCache` | `OfflineVerifyEntry` / `OfflineVerifyAll` | 单条 / 全量 SHA256 重校验 |
| `CleanupCache` | `OfflineCleanupCache` | 三模式清理，在用受保护 |
| `RemoveCacheEntry` | `OfflineRemoveEntry` | 删单条（不可恢复，前端确认） |
| `LookupImage` / `LookupExtension` | `OfflineLookupImage` / `OfflineLookupExtension` | 命中查询（命中前必校验） |
| `PromoteImage` / `PromoteExtension` | `OfflinePromoteImage` / `OfflinePromoteExtension` | 提升到缓存 |
| `ImportEntry` | `OfflineImportFile` | **手工导入**（§5.14.9a）：把用户选定路径的文件**复制**为一条缓存（`image`/`apk`/`pecl`）+ 写 manifest + 发 `cache:promote`；走 `cache-import` 任务，源文件不动 |
| `ClearTempDir` | `OfflineClearTempDir` | 清空临时目录 + 发事件 |

> **扩展固化镜像的三个能力不在这张表里**（总纲 §5.14.2 两槽位 / v2.9.14 需求 ③）：`LookupExtImage(version)`、`LoadExtImage(ctx, version)`、`PromoteExtImage(version, ref, tmpTar)` 挂在 `cache.Manager` 上，**不经 `OfflineService` 门面**，因此 `app.go` 的绑定方法数不随之增加。理由是它们是安装/恢复链路**内部步骤**（`LifecycleService.specFor` 在 `ImageExists` 探不到 `phpo/php:{ver}` 时调 `LoadExtImage` 零网络恢复；`ExtensionService.promoteCommitted` 调 `PromoteExtImage`），不是用户触发的运维动作。对应槽位是 `image-extensions.tar` / `manifest.extensions_image`，**与基座的 `image.tar` / `manifest.image` 各占一份**——共用槽位等于每次「应用扩展」把基座缓存覆盖掉，下次装基座即 load 到名实不符的镜像。`PromoteExtImage` 同样发 `cache:promote`（**不新增事件名**）。

## 3. 命中裁决顺序（硬约束）

```
Lookup(kind, version)
  → 文件存在? ──否→ MISS（镜像：先探本机镜像库；扩展：联网下载）
        │是
  → manifest 有记录且 sha256 匹配? ──否→ CORRUPTED（发 cache:corrupted → 落入 MISS 分支）
        │是
  → HIT（零网络，发 cache:hit）
```

镜像的 MISS 分支内部再分一级（AGENTS.md §5.14.3 「离线缓存 > 本机 Docker 镜像库 > 网络」）：`ImageExists(ref)` 命中即 `action=local` 就地 `docker save`，全程不碰网络；探不到才 `action=pull` 联网。探针报错必须上抛，不得静默当作「本机没有」。扩展不参与这一级。

任何安装入口（`App.Install`、`ExtApply`）第一步必为 Lookup；跳过查缓存即违反硬红线 8（§0.2-21）。

**根的唯一性**（§5.15）：上表所有读写都经 `Env.OfflineRoot` 取**当前生效缓存根**（默认 `{PHPO_HOME}/offline`，自定义即完全取代默认）。改根走 `App.SetOfflineRoot → config.yaml → container.Rebind`，装配期分发给各门面的 `Env` 是值拷贝，**不换图就仍在旧根读写**——故 `Rebind` 是改根链路的必要步骤，队列非空时改根直接拒（`errs.TaskBusy`）。

## 4. 与 Docker 清洁机制的协同（§5.14.13）

| 场景 | 协同行为 |
|------|---------|
| 安装（命中） | 缓存提供 image.tar → `docker load` → 容器走清洁流程 |
| 安装（未命中） | 先 `ImageExists` 探本机镜像库：已有即 `docker save`（`action=local`，零网络）→ 提升到缓存；探不到才 `docker pull` → `docker save` 到缓存 → 容器走清洁流程 |
| 卸载服务 | **不动缓存** |
| 重装服务 | **优先命中缓存**（零网络） |
| 孤儿扫描 | **不扫描缓存** |
| 激进清理 | **可选清理缓存**（用户确认后） |
| 状态校准 | **不动缓存** |

关键约束：**缓存不受 Docker 清洁机制影响；缓存与 Docker 资源完全解耦**。

## 5. 幂等与原子

- Lookup/Verify 纯读，幂等。
- Promote 用 `moveFile`（rename，失败退化 copy）+ `SaveManifest` 原子写，重复提升收敛同一态。
- ClearTempDir：目录不存在视为已清空（no-op，仍发事件）。
