# 编码行为准则

> 对应 AGENTS.md §3.4（v2.7 新增）/ §0.2-23、**§0.2-38**（v2.9.14 追加的文风条款）/ §9 R83–R87 / §12.5、**§12.11** 自查清单 / 工单 T704。本节约束 Agent 编写、修改、重构本项目代码的行为，**以及写文档与界面文案的文风（第 7 节）**。冲突以 AGENTS.md 为准。

## 0. 四准则一览

**编码前思考 · 简洁优先 · 精准修改 · 目标驱动执行**

## 1. 编码前思考（§3.4.1）

1. 明确假设，不确定时**询问而非猜测**；假设须有依据（本文件条款/原型源码/用户指示）。
2. 存在歧义时**列出多种解释**，不默默选定单一方案。
3. 有明显更简单做法时**直接指出**（如已有 `log/slog` 就别再造轮子）。
4. 发现代码矛盾/逻辑不一致时**暂停并报告**，等裁决（§0.2-22），不「绕过」默默修复。

## 2. 简洁优先（§3.4.2）

1. 用**最少代码**解决问题；能 10 行写完绝不写 100 行。
2. **不为一次性需求建抽象层**；重复 ≥2 次才考虑提取。
3. **不盲目加扩展性/可配置性**（YAGNI，不为「未来可能」设计）。
4. 可大幅精简者**主动重写**（不牺牲可读性/正确性）。
5. 校验标准：5 年 Go 经验工程师能否 30 秒看懂？不能则简化。

## 3. 精准修改（§3.4.3）

1. **仅改与当前任务直接相关**的代码。
2. **不顺手优化**相邻代码/注释/排版（无关问题仅文字提醒）。
3. **不重构能正常运行的模块**——「能跑就不要动」是铁律。
4. **严格匹配现有风格**（命名/错误处理习惯，如 `if err != nil { return err }`）。
5. 因本次修改产生的**无效导入/废弃变量可直接删除**。
6. 发现**原有**死代码/冗余 → **仅提醒，不擅自删除**（删除属重构，需授权）。

## 4. 目标驱动执行（§3.4.4）

1. 开工前**定义清晰、可落地的成功标准**。
2. 「修复 Bug」→「**先写用例复现**再调试至通过」。
3. 「新增校验」→「针对异常输入**写测试用例**，覆盖正常/边界/异常，全绿」。
4. 「重构」→「确保**原有全部测试通过**」（重构前跑基线，改后再跑）。
5. 多步骤任务**先输出执行计划**，每步标注验证方式；每步完成先验证再进下一步。

## 5. 与 §0.2 的关系（§3.4.5）

| 章节 | 约束对象 | 内容 |
|------|---------|------|
| §0.2 | Agent 对项目的整体行为 | 项目级「不要做什么」 |
| §3.4 | Agent 的编码行为 | 编码级「怎么做」 |

二者互补：§0.2 划定禁区，§3.4 规定工作方法。

## 6. 明确禁止（§3.4.6）

- ❌ 不确定时猜测；歧义时默默选定；有更简单做法不指出；发现矛盾不停下。
- ❌ 冗余实现、过度抽象、为未来设计。
- ❌ 顺手改相邻代码/注释/格式；重构能跑的代码；擅自删死代码（应仅提醒）。
- ❌ 无明确成功标准就开工；无测试用例就声称「修复完成」；多步骤任务不先规划。

## 7. 文风：任何文档必须说人话（AGENTS.md §0.1.2 · §0.2 规则 38，v2.9.14 追加）

这条准则管的是**写下来的字**，不是代码。它约束 `AGENTS.md`、`docs/` 全部文档、`任务工单.md`、`实施顺序.md`、代码注释，以及**给用户看的文案**（前端 `locales/`、向导提示、错误信息）。

**为什么要有这条**：本项目多次出现过同一种返工——用户读完写好的文档或界面文案，回一句「说人话」。原因是写的人把当轮对话里的内部词当成了通用语言：「权威集」「派生态」「落地链」「归一」「去帧」这些词只在实现者脑子里有图，读者手上没有词典。

**怎么写（三步，顺序不能换）**：

1. **先说这是干什么的**。一句话给目的或结果，不先铺条件、不先给字段名。
   - ✗ 「`ExtStatus` 在返回前执行一次实测归一回写快照回流链路」
   - ✓ 「打开「管理扩展」时，后端到容器里现查一次哪些扩展开着，再把这份结果写回权威库、推给界面」
2. **再说这种错用户看得见什么**。不要只写「必须 X」，要写「不 X 会怎样、界面上出现哪一行字」。
   - ✗ 「否则违反硬红线 4 造成界面失真」
   - ✓ 「拿不到实测结果时，界面显示上次存库的那一套并写一行『非实时』，不会整片显示成没装」
3. **最后说怎么回来**。恢复路径要具体到用户点哪里，或说明下一步会自愈。
   - ✗ 「异常需人工介入」
   - ✓ 「腾出那个端口或再改一次端口，站点即自愈」

**四条不得**：

- ❌ 拿术语当解释：本项目自造／借用的词**首次出现要顺带说清指什么**。
- ❌ 拿条款编号当正文：`见 §5.16.2` 只是索引，那一段本身必须读得懂。
- ❌ 把实现细节写进给用户看的文案：函数名、分支名、事件名留在总纲和注释里，界面只说**结果和下一步**。
- ❌ 为了通俗而失真：说人话**不放松**准确性——数字仍须命令实测（§0.2 规则 2）、路径仍守 §0.1.1 记法、口径仍与既有条款一致。

**例外**：表格里的字段名、文件路径、真实命令照写，它们是精确指针而不是文风；但包住它们的那句话必须读得懂。

**怎么算合格（可执行判据）**：把这段拿给**没参与过当轮讨论的同事**读。他能复述「改了什么 / 为什么会错 / 怎么验证」即合格；他要反问才能读懂，就是重写的时候。
