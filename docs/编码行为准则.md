# 编码行为准则

> 对应 AGENTS.md §3.4（v2.7 新增）/ §0.2-23 / §9 R83–R87 / §12.5 自查清单 / 工单 T704。本节约束 Agent 编写、修改、重构本项目代码的行为。冲突以 AGENTS.md 为准。

## 0. 四准则一览

**编码前思考 · 简洁优先 · 精准修改 · 目标驱动执行**

## 1. 编码前思考（§3.4.1）

1. 明确假设，不确定时**询问而非猜测**；假设须有依据（本文件条款/原型源码/用户指示）。
2. 存在歧义时**列出多种解释**，不默默选定单一方案。
3. 有明显更简单做法时**直接指出**（如已有 `log/slog` 就别再造轮子）。
4. 发现代码矛盾/逻辑不一致时**暂停并报告**，等裁决（§0.2-22），不「绕过」默默修复。

## 2. 简洁优先（§3.4.2）

1. 用**最少代码**解决问题；能 10 行写完绝不写 100 行。
2. **不为一次性需求建抽象层**；重复 ≥2 次才考虑提取。
3. **不盲目加扩展性/可配置性**（YAGNI，不为「未来可能」设计）。
4. 可大幅精简者**主动重写**（不牺牲可读性/正确性）。
5. 校验标准：5 年 Go 经验工程师能否 30 秒看懂？不能则简化。

## 3. 精准修改（§3.4.3）

1. **仅改与当前任务直接相关**的代码。
2. **不顺手优化**相邻代码/注释/排版（无关问题仅文字提醒）。
3. **不重构能正常运行的模块**——「能跑就不要动」是铁律。
4. **严格匹配现有风格**（命名/错误处理习惯，如 `if err != nil { return err }`）。
5. 因本次修改产生的**无效导入/废弃变量可直接删除**。
6. 发现**原有**死代码/冗余 → **仅提醒，不擅自删除**（删除属重构，需授权）。

## 4. 目标驱动执行（§3.4.4）

1. 开工前**定义清晰、可落地的成功标准**。
2. 「修复 Bug」→「**先写用例复现**再调试至通过」。
3. 「新增校验」→「针对异常输入**写测试用例**，覆盖正常/边界/异常，全绿」。
4. 「重构」→「确保**原有全部测试通过**」（重构前跑基线，改后再跑）。
5. 多步骤任务**先输出执行计划**，每步标注验证方式；每步完成先验证再进下一步。

## 5. 与 §0.2 的关系（§3.4.5）

| 章节 | 约束对象 | 内容 |
|------|---------|------|
| §0.2 | Agent 对项目的整体行为 | 项目级「不要做什么」 |
| §3.4 | Agent 的编码行为 | 编码级「怎么做」 |

二者互补：§0.2 划定禁区，§3.4 规定工作方法。

## 6. 明确禁止（§3.4.6）

- ❌ 不确定时猜测；歧义时默默选定；有更简单做法不指出；发现矛盾不停下。
- ❌ 冗余实现、过度抽象、为未来设计。
- ❌ 顺手改相邻代码/注释/格式；重构能跑的代码；擅自删死代码（应仅提醒）。
- ❌ 无明确成功标准就开工；无测试用例就声称「修复完成」；多步骤任务不先规划。

## 7. 对应风险（§9）与自查（§12.5）

R83 未守准则致质量下降 / R84 猜测偏离需求 / R85 过度抽象 / R86 顺手改引入 Bug / R87 无验证标准谎报完成。每个 PR 按 §12.5 四组清单逐项自查；违反项必须整改。
