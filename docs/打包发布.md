# 打包发布

> 对应 AGENTS.md §11.1（三平台安装包）/ §5.9（升级双校验）/ §0.2-18 硬红线 6 / 工单 T701–T703、T704。描述出包、签名、校验产物与 CI 一键发布。冲突以 AGENTS.md 为准。

## 1. 交付物（§11.1）

| 平台 | 产物 | 工具 |
|------|------|------|
| Windows | `phpo-setup-x64.exe` + `.sig` | NSIS（`build/windows/nsis/installer.nsi`） |
| macOS | `phpo-x64.dmg`（含公证）+ `.sig` | `wails3 tool package -format dmg` |
| Linux | `phpo-x86_64.AppImage` / `phpo_<ver>_amd64.deb` / `.rpm` + `.sig` | `wails3 tool package -format deb\|rpm -config build/linux/nfpm.yaml`（goreleaser/nfpm v2） |
| 全平台 | `checksums.txt` | `scripts/gen-checksums.sh` |

每个产物附 `.sig`（Ed25519），并汇总进 `checksums.txt`（`<sha256>  <basename>`）。

## 2. 构建链（Taskfile）

- **wails3 打包模型**：`wails3 build`/`package` 委托给 Taskfile（go-task），**不接受** `-platform`/`-o`/`-nsis` 参数。真实编译 = `go build -trimpath -ldflags "-s -w" -o build/bin/phpo .`。
- 任务经 `wails3 task <name>` 执行（task 二进制不单独在 PATH；wails3 CLI v3.0.0-beta.23）。
- `package` → deb；`package:linux` → deb + rpm；`package:windows` → makensis；`package:darwin` → dmg（签名/公证见 §4）。
- deb/rpm 必需 `-config build/linux/nfpm.yaml`；dmg 可选 config。
- **`frontend:build` 依赖 `bindings`**：`frontend/bindings/` 是 `wails3 generate bindings` 的生成物且被 gitignore（AGENTS.md §4.1），全新 checkout 里并不存在，而 `pnpm build` 的 `vue-tsc --noEmit` 静态导入它（17 个 `api/*.ts` 中 15 个导入，缺它即 20 处 `TS2307` + 6 处派生 `TS7006`）。Taskfile 把生成挂成 `deps: [bindings]`，于是 `build` → `package:*` 与 CI/发布链一律先出绑定再编译，不再依赖「开发者记得手工跑一次」。`wails3 task --dry package:linux` 的首行即 `[bindings]`。

## 3. Linux 打包（nfpm）

`build/linux/nfpm.yaml`（标准 nfpm YAML，顶层 `depends` 而非 `deb:`/`rpm:` 段）：

- `depends: [libwebkit2gtk-4.1-0]`；`overrides.rpm.depends: [webkit2gtk4.1]`。
- `contents`：`build/bin/phpo → /usr/bin/phpo(0755)`、`phpo.desktop → /usr/share/applications`、icons → `hicolor/{128,256,512}x…/apps/phpo.png`。
- `scripts.postinstall: build/linux/postinstall.sh`（best-effort `update-desktop-database` + `gtk-update-icon-cache`）。

> **登记一处待裁决的产物缺陷（未修）**：上面两条依赖名是 **GTK3/webkit2gtk-4.1** 时代的写法，而按 §6.1，
> 本机实际链接的是 **GTK4 / webkitgtk-6.0 / libsoup-3.0**（`ldd build/bin/phpo` 可验）。后果：在干净系统上
> 装完 deb/rpm 后 `phpo` 会因缺 `libwebkitgtk-6.0.so.0` 而起不来，包管理器却不会报缺依赖。
> 修它要同时定 deb 与 rpm 两套包名（`libwebkitgtk-6.0-4` / `webkitgtk6.0` 一类）并重新出包验证，
> 属独立一轮工作，未与本轮 CI 修复混做。

## 4. 代码签名与公证

- **签名约定**（与 `internal/updater/verifier.go` 严格一致）：`signature = base64(Ed25519(lowercase-sha256-hex 字符串字节))`——被签消息是 64 字节 ASCII hex 串本身，**不是**文件字节。
- `scripts/sign-release.sh`（子命令 `genkey` / `pubkey` / `sign`）：
  - `genkey`：生成 Ed25519 私钥（仅存发布机，`.gitignore` 屏蔽 `*.key`/`*.pem`）。
  - `pubkey`：导出 32 字节公钥 → `base64 -w0` → 写入 `internal/updater/signing/public.key`（唯一入库公钥，`go:embed` 随包分发，见 `updater/embed.go`；仓库不再有 `build/signing/`）。
  - `sign`：`sha256(file)` → `printf '%s' "$h"` → `openssl pkeyutl -sign -rawin -in hashfile | base64 -w0 > file.sig`（跳过非文件如 `.app` 目录）。
- 公钥格式：`base64.StdEncoding(raw 32B ed25519 pubkey)`，`TrimSpace`；与 Go `ed25519.Verify` 跨工具兼容（已实证 openssl↔Go）。
- macOS 公证：Developer ID 签名 + `notarytool` 公证（`entitlements.plist` 就位）；Linux 无强制签名；Windows EV 证书。

## 5. 校验产物与发布清单

### 5.1 `checksums.txt`（`scripts/gen-checksums.sh`）

`BIN_DIR`（默认 `build/bin`）扫描发布名样式文件，跳过 `*.sig`/`checksums.txt`，输出 `<sha256>  <basename>` 到 `checksums.txt`。

### 5.2 发布清单 `manifest.json`（`scripts/gen-release-manifest.sh`）

应用内「检查更新」要拉的那份 JSON（远端契约见 [应用升级](./应用升级.md) §2 / AGENTS.md §5.9）。环境变量：`VERSION`（必填，不含 `v`）、`BIN_DIR`（默认 `out`）、`OUT`、`ASSET_BASE`（缺省按 `GITHUB_REPOSITORY` + `GITHUB_REF_NAME` 拼 GitHub Release 直链——Gitee 镜像源发布时显式指过去）、`CHANGELOG`、`DOWNLOAD_PAGE`。

- 扫 `BIN_DIR` 逐份算 SHA256 与体积，按扩展名归成 `(os, format)`：**`.exe`→windows/exe · `.dmg`→darwin/dmg · `.AppImage`→linux/appimage · `.deb`→linux/deb · `.rpm`→linux/rpm**，写进 `assets`；同一 `os/format` 只保留先出现的一份（客户端 `resolvePlatform` 也只取一颗）。
- **未签名的产物不进清单**：无 `*.sig` 或 `.sig` 为空即跳过并告警——没有签名客户端必然验签失败（硬红线 6），宁可不发布这版更新；一份签名包都没有则退出码 1、不生成清单。
- `.sig` 由 `base64 -w0` 写出、末尾带换行，`base64.StdEncoding.DecodeString` 不接受换行，故读取时 `tr -d '\r\n'` 压成单行。
- 顶层另写 `version` / `changelog` / `download_page`（后者缺席即客户端不渲染「打开下载页」按钮）；`url`/`sha256`/`signature` 留空属正常——多平台清单靠 `assets` 派生，单包清单才写顶层。
- 产物文件名必须 URL 安全（`[A-Za-z0-9._-]+`），否则跳过：URL 是直拼进 JSON 字符串的，不做百分号编码。

## 6. CI 一键出包（`.github/workflows/release.yml`）

- matrix：`[ubuntu-24.04/linux, windows-latest, macos-14/darwin]`，各自 `task package:<os>`。
- 汇总到 `out/`（`download-artifact@v8` 三处一律 `merge-multiple: true`，产物**平铺**入 `out/`，不套
  `pkg-<target>/` 子目录——`gen-checksums.sh` 用 `find out -maxdepth 1 -type f`，发布步骤用 `files: out/*`，
  两处都按平铺消费；钉死该输入后 download-artifact 各主版本行为一致）；发布 job：
  - `bash scripts/verify-signing-guard.sh /tmp/phpo-sign.pem internal/updater/signing/public.key`（私钥↔内嵌公钥必须同一把，否则客户端验签全失败；与 dry-run `guard_only` 作业复用同一脚本）
  - `PHPO_SIGNING_KEY=/tmp/phpo-sign.pem bash scripts/sign-release.sh sign out/*`
  - `BIN_DIR=out bash scripts/gen-checksums.sh`
  - `VERSION=… DOWNLOAD_PAGE=<发布页> bash scripts/gen-release-manifest.sh`（§5.2；`if: env.PHPO_SIGNING_KEY != ''`，无签名即不出清单）
  - `softprops/action-gh-release@v3` 上传产物 + `.sig` + `checksums.txt` + `manifest.json`
- 手动 `workflow_dispatch` 时 `github.ref_name` 是**分支名**而非标签，故发布标签与 `DOWNLOAD_PAGE` 里的 tag 一律由版本号推出（`v${{ steps.ver.outputs.version }}`）。
- actionlint 已校验通过（T703）。


### 6.1 Linux runner 与工具链（三条工作流同一口径）

`ci.yml` / `lint.yml` / `release.yml` 的 Linux 作业一律 `ubuntu-24.04`，且 apt 装的是 **GTK4 一路**的开发头：

```
libgtk-4-dev libwebkitgtk-6.0-dev libsoup-3.0-dev libglib2.0-dev libx11-dev build-essential pkg-config
```

三个原因，都不是可调教的实现细节：

1. **Wails v3.0.0-beta.23 在 Linux 上走 GTK4**（全仓无 `-tags gtk3`），其 cgo 要求
   `pkg-config: gtk4 webkitgtk-6.0 libsoup-3.0 gio-unix-2.0 glib-2.0 gobject-2.0 + x11`。
   `ubuntu-22.04` 的 apt 源里**没有** `libwebkitgtk-6.0-dev`，装旧的 `libwebkit2gtk-4.1-dev` 编不过，
   于是 `go build ./...`、`go vet ./...`、以及 `go install github.com/wailsapp/wails/v3/cmd/wails3@…`
   （它自身要编译 `internal/operatingsystem/webkit_linux.go`，同一套 pkg-config 依赖）三处恒红。
   **顺序要求**：`release.yml` 的工具链步骤必须排在「Install Wails CLI」**之前**。
2. **actionlint 把 node20 运行时判为弃用（error）**，`workflow-lint` 作业因此恒红。现一律跟到跑
   node24 的主版本：`checkout@v5` · `setup-go@v6` · `setup-node@v6` · `pnpm/action-setup@v5` ·
   `upload-artifact@v7` · `download-artifact@v8` · `action-gh-release@v3`
   （`reviewdog/action-actionlint@v1` 是 docker 容器作业，不受该规则约束）。
3. **前端作业的 pnpm 主版本必须是 12**（`pnpm/action-setup` 的 `version: 12`，三条工作流同一值）：
   `frontend/pnpm-workspace.yaml` 只有 `allowBuilds:`（放行 `esbuild`／`vue-demi` 的安装期构建脚本）、
   **没有 `packages:`**，pnpm 9 读它即 `ERROR packages field missing or empty`，`pnpm -C frontend install
   --frozen-lockfile` 第一步退出码 1；pnpm 10+ 才允许该文件是纯配置。本机用 pnpm 12.4.1，
   `pnpm-lock.yaml` 的 `lockfileVersion: '9.0'` 由 pnpm 12 向后兼容读取，故 CI 跟本机而非相反
   （往工作区文件塞空 `packages:` 迁就旧主版本，等于让本机出包链路与 CI 分叉）。

> `keep`。第一轮把它由 `10` 改为 **`0`**（该行注释原先写「保留最近 1 次运行，设为 0 则全部删除」，与值本就不一致）
> 并推送，之后用户在登录态手动 `workflow_dispatch` 触发了 **两次**（run #1 `35930485021`、#2 `35930646395`，head 均为
> `43ecd95`），**两次都在 5s 内 `failure`**，annotation 只有 `Process completed with exit code 1.`，仓库的 **92** 条
> 运行记录**一条也没被删掉**。用户贴回的完整日志给出了决定性判据：
> `Fetching workflow runs` → `failed to determine base repo: failed to run git: fatal: not a git repository (or any of
> the parent directories): .git` → `[FATAL] 50: gh run list "${GH_RUN_LIST_ARGS[@]}"`。据此**两层根因**：
> ① **作业根本没有仓库上下文**——本工作流**没有 `actions/checkout` 步骤**，工作目录里不存在 `.git`，动作内部的
> `gh` 2.101.0 只能靠 git remote 探测仓库，于是在第一条 `gh run list` 上就死掉（两次各 5s 即失败、92 条记录一条未删，与此一致）。
> 修法是 job 级 `env: GH_REPO: ${{ github.repository }}`——`GH_REPO` 是 `gh` 的官方仓库上下文覆盖项，**优先于 git
> 探测**，因此不必为了删运行记录而克隆整个仓库；退路是照该动作自身 CI 的做法补一步 `actions/checkout`。
> ② **`keep: 0` 本身落在未定义区**——该动作的换算是「`KEEP > 0` 才 +1（+1 给正在跑的这一条自己留位），随后
> `tail -n +$KEEP` 取待删集」，故 `keep=0` 既跳过 +1、又要把「第 0 行」当起点。本机 `tail` 实测即不一致（uutils
> coreutils 0.10.0：管道输入时输出**空** ⇒ 一条都不删、作业却判绿；读文件时输出**全部** ⇒ 连正在跑的这条一起删），
> runner 上的 GNU tail 未实测，**不能**把「清空」寄托在这里。现取值改为 **`keep: 1`**，语义是明确的那一条：跳过最新
> 一行（即本清理作业自身，GitHub 也不允许删自己正在跑的记录），其余全部删除 ⇒ All workflows 清到只剩这一条。
> **副作用照旧要写清**：它按 `schedule: 0 0 * * 0` 每周复发 ⇒ **运行历史从此每周被清空到剩一条**，#40／#41／#43／#44
> 这些被当作判据的历史运行已不再可查（**同一次清理把上文引用的 run #45 两条记录也一并删掉了——2026-09-24 按 id 直查即 `404`**；
> 其判定内容与 run id 已逐条落在本节与 [CHANGELOG](./CHANGELOG.md)，故**判定不因
> 记录被删而失效**；但今后引用某个历史 run 的界面须在清掉前取证）。想保留窗口就把 `keep` 调大——这是唯一开关
> （该动作 clamp 到 0–10）。**真机判定（run #3 `35931973231`，head `bd36c05`，workflow_dispatch）**：Cleanup
> `completed`／**`success`**（23:07:24Z → 23:08:49Z，约 1m25s，不再是在第一条 `gh run list` 上 5s 死掉），
> 且 `GET /actions/runs` 的 `total_count` 由 **92 → 1** —— 盘上只剩这一次清理作业自身，两层根因的修法同时得证
> （`GH_REPO` 给了仓库上下文；`keep: 1` 如预期跳过了最新一行）。**由此得出一条今后引用 CI 证据的硬规矩**：
> 每周清一次意味着任何历史 run 的界面最多活 7 天，**引用前必须先取证**（本页与 [CHANGELOG](./CHANGELOG.md)
> 逐条留 run id + 判定文本正是为此）。**另需登记一处文档漂移**：`.github/workflows/` 实为 **4** 条
> （`ci`／`lint`／`release`／`cleanup-actions`），而本节上文与 AGENTS.md §4.1／§11.3 仍按「三条工作流」表述；
> 改总纲属 §13 变更提案，未在本文擅自收敛。

> `ci.yml` / `lint.yml` 已落地（[目录规范](./目录规范.md) §8 不再登记）；`release.yml` 为 M7 出包主链路。三条工作流的前端作业都必须先有 TS 绑定：`ci.yml` 走 `wails3 task frontend:build`，`lint.yml` 在 `vue-tsc --noEmit` 前显式 `wails3 generate bindings -ts -clean`，`release.yml` 经 `task package:<os>` 自动带上（见 §2）。真机装/卸/升/回滚冒烟属 T705（留用户/CI）。
