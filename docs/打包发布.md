# 打包发布

> 对应 AGENTS.md §11.1（三平台安装包）/ §5.9（升级双校验）/ §0.2-18 硬红线 6 / 工单 T701–T703、T704。描述出包、签名、校验产物与 CI 一键发布。冲突以 AGENTS.md 为准。

## 1. 交付物（§11.1）

| 平台 | 产物 | 工具 |
|------|------|------|
| Windows | `phpo-setup-x64.exe` + `.sig` | NSIS（`build/windows/nsis/installer.nsi`） |
| macOS | `phpo.dmg`（ad-hoc 签名；Developer ID + 公证未接入）+ `.sig` | `.app` bundle 由 `Taskfile.yml` 的 `package:darwin` 自建 → `wails3 tool package -format dmg`（见 §6.4） |
| Linux | `phpo-x86_64.AppImage` / `phpo_<ver>_amd64.deb` / `.rpm` + `.sig` | `wails3 tool package -format deb\|rpm -config build/linux/nfpm.yaml`（goreleaser/nfpm v2） |
| 全平台 | `checksums.txt` | `scripts/gen-checksums.sh` |

每个产物附 `.sig`（Ed25519），并汇总进 `checksums.txt`（`<sha256>  <basename>`）。

## 2. 构建链（Taskfile）

- **wails3 打包模型**：`wails3 build`/`package` 委托给 Taskfile（go-task），**不接受** `-platform`/`-o`/`-nsis` 参数。真实编译 = `go build -trimpath -ldflags "-s -w -X phpo/internal/app.Version=$(bash scripts/version.sh)" -o build/bin/phpo{{exeExt}} .`（`exeExt` 是 task 的模板函数：windows → `.exe`，其余平台 → 空串；该 `-X` 即 §6.2 的第 1 条版本链）。
- 任务经 `wails3 task <name>` 执行（task 二进制不单独在 PATH；wails3 CLI v3.0.0-beta.23）。
- `package` → deb；`package:linux` → deb + rpm；`package:windows` → makensis（三条路径宏传**绝对路径**，见 §6.5）；`package:darwin` → 自建 `.app` bundle（含版本注入 + ad-hoc 签名）→ dmg（正式签名/公证见 §4）。
- deb/rpm 必需 `-config build/linux/nfpm.yaml`；dmg 可选 config，且**要求 `{out}/{name}.app` 已存在**（beta.23 不生成 bundle，见 §6.4）。
- **`frontend:build` 依赖 `bindings`**：`frontend/bindings/` 是 `wails3 generate bindings` 的生成物且被 gitignore（AGENTS.md §4.1），全新 checkout 里并不存在，而 `pnpm build` 的 `vue-tsc --noEmit` 静态导入它（17 个 `api/*.ts` 中 15 个导入，缺它即 20 处 `TS2307` + 6 处派生 `TS7006`）。Taskfile 把生成挂成 `deps: [bindings]`，于是 `build` → `package:*` 与 CI/发布链一律先出绑定再编译，不再依赖「开发者记得手工跑一次」。`wails3 task --dry package:linux` 的首行即 `[bindings]`。

## 3. Linux 打包（nfpm）

`build/linux/nfpm.yaml`（标准 nfpm YAML，顶层 `depends` 而非 `deb:`/`rpm:` 段）：

- `depends: [libwebkit2gtk-4.1-0]`；`overrides.rpm.depends: [webkit2gtk4.1]`。
- `contents`：`build/bin/phpo → /usr/bin/phpo(0755)`、`phpo.desktop → /usr/share/applications`、icons → `hicolor/{128,256,512}x…/apps/phpo.png`。
- `scripts.postinstall: build/linux/postinstall.sh`（best-effort `update-desktop-database` + `gtk-update-icon-cache`）。

> **登记一处待裁决的产物缺陷（未修）**：上面两条依赖名是 **GTK3/webkit2gtk-4.1** 时代的写法，而按 §6.1，
> 本机实际链接的是 **GTK4 / webkitgtk-6.0 / libsoup-3.0**（`ldd build/bin/phpo` 可验）。后果：在干净系统上
> 装完 deb/rpm 后 `phpo` 会因缺 `libwebkitgtk-6.0.so.0` 而起不来，包管理器却不会报缺依赖。
> 修它要同时定 deb 与 rpm 两套包名（`libwebkitgtk-6.0-4` / `webkitgtk6.0` 一类）并重新出包验证，
> 属独立一轮工作，未与本轮 CI 修复混做。

## 4. 代码签名与公证

- **签名约定**（与 `internal/updater/verifier.go` 严格一致）：`signature = base64(Ed25519(lowercase-sha256-hex 字符串字节))`——被签消息是 64 字节 ASCII hex 串本身，**不是**文件字节。
- `scripts/sign-release.sh`（子命令 `genkey` / `pubkey` / `sign`）：
  - `genkey`：生成 Ed25519 私钥（仅存发布机，`.gitignore` 屏蔽 `*.key`/`*.pem`）。
  - `pubkey`：导出 32 字节公钥 → `base64 -w0` → 写入 `internal/updater/signing/public.key`（唯一入库公钥，`go:embed` 随包分发，见 `updater/embed.go`；仓库不再有 `build/signing/`）。
  - `sign`：`sha256(file)` → `printf '%s' "$h"` → `openssl pkeyutl -sign -rawin -in hashfile | base64 -w0 > file.sig`（跳过非文件如 `.app` 目录）。
- 公钥格式：`base64.StdEncoding(raw 32B ed25519 pubkey)`，`TrimSpace`；与 Go `ed25519.Verify` 跨工具兼容（已实证 openssl↔Go）。
- macOS 公证：Developer ID 签名 + `notarytool` 公证（`entitlements.plist` 就位）；Linux 无强制签名；Windows EV 证书。

## 5. 校验产物与发布清单

### 5.1 `checksums.txt`（`scripts/gen-checksums.sh`）

`BIN_DIR`（默认 `build/bin`）扫描发布名样式文件，跳过 `*.sig`/`checksums.txt`，输出 `<sha256>  <basename>` 到 `checksums.txt`。

### 5.2 发布清单 `manifest.json`（`scripts/gen-release-manifest.sh`）

应用内「检查更新」要拉的那份 JSON（远端契约见 [应用升级](./应用升级.md) §2 / AGENTS.md §5.9）。环境变量：`VERSION`（必填，不含 `v`）、`BIN_DIR`（默认 `out`）、`OUT`、`ASSET_BASE`（缺省按 `GITHUB_REPOSITORY` + `GITHUB_REF_NAME` 拼 GitHub Release 直链——**`release.yml` 现在总是显式传入解析出的发布标签**，因为手动 dispatch 时 `GITHUB_REF_NAME` 是分支名，拼出来会指向不存在的 `releases/download/main/…`；脚本内的回落仅供本地手工出清单与 Gitee 镜像源发布），`CHANGELOG`、`DOWNLOAD_PAGE`。

- 扫 `BIN_DIR` 逐份算 SHA256 与体积，按扩展名归成 `(os, format)`：**`.exe`→windows/exe · `.dmg`→darwin/dmg · `.AppImage`→linux/appimage · `.deb`→linux/deb · `.rpm`→linux/rpm**，写进 `assets`；同一 `os/format` **只保留先出现的一份并跳过其余**（客户端 `resolvePlatform` 也只取一颗，见 §6.6 第 2 层）。「先出现」的顺序钉为 **`LC_ALL=C`**，不随 runner 的 locale 变（§6.6 第 3 层）。判重发生在签名校验**之后**——未签名那份本来就不进清单，先登记会把同平台唯一那份已签名的包挡掉。
- **未签名的产物不进清单**：无 `*.sig` 或 `.sig` 为空即跳过并告警——没有签名客户端必然验签失败（硬红线 6），宁可不发布这版更新；一份签名包都没有则退出码 1、不生成清单。
- `.sig` 由 `base64 -w0` 写出、末尾带换行，`base64.StdEncoding.DecodeString` 不接受换行，故读取时 `tr -d '\r\n'` 压成单行。
- 顶层另写 `version` / `changelog` / `download_page`（后者缺席即客户端不渲染「打开下载页」按钮）；`url`/`sha256`/`signature` 留空属正常——多平台清单靠 `assets` 派生，单包清单才写顶层。
- 产物文件名必须 URL 安全（`[A-Za-z0-9._-]+`），否则跳过：URL 是直拼进 JSON 字符串的，不做百分号编码。

## 6. CI 一键出包（`.github/workflows/release.yml`）

- matrix：`[ubuntu-24.04/linux, windows-latest, macos-14/darwin]`，各自 `task package:<os>`。
- `Upload staged artifacts` 的 `path` 是**四行分发物白名单**（`build/bin/*.deb` / `*.rpm` / `*.dmg` / 精确名
  `build/bin/phpo-setup-x64.exe`），**不是** `build/bin/*`——后者会把 `go build` 的裸可执行文件一并送进 Release，
  理由与三层防线见 §6.6。
- 汇总到 `out/`（`download-artifact@v8` 三处一律 `merge-multiple: true`，产物**平铺**入 `out/`，不套
  `pkg-<target>/` 子目录——`gen-checksums.sh` 用 `find out -maxdepth 1 -type f`，发布步骤用 `files: out/*`，
  两处都按平铺消费；钉死该输入后 download-artifact 各主版本行为一致）；发布 job：
  - `bash scripts/verify-signing-guard.sh /tmp/phpo-sign.pem internal/updater/signing/public.key`（私钥↔内嵌公钥必须同一把，否则客户端验签全失败；与 dry-run `guard_only` 作业复用同一脚本）
  - `PHPO_SIGNING_KEY=/tmp/phpo-sign.pem bash scripts/sign-release.sh sign out/*`
  - `BIN_DIR=out bash scripts/gen-checksums.sh`
  - `VERSION=… ASSET_BASE=<发布直链> DOWNLOAD_PAGE=<发布页> bash scripts/gen-release-manifest.sh`（§5.2；`if: env.PHPO_SIGNING_KEY != ''`，无签名即不出清单）
  - `softprops/action-gh-release@v3` 上传产物 + `.sig` + `checksums.txt` + `manifest.json`
- **版本与发布标签在 `Resolve version and tag`（步骤 id `ver`）一处裁决**，唯一的真实来源是 `wails.json` 的
  `productVersion`（即 `bash scripts/version.sh`，也就是二进制内嵌的那一份）。该步骤输出 `version` 与 `tag` 两个量，
  下游三步（清单的 `ASSET_BASE`/`DOWNLOAD_PAGE`、`tag_name`、`prerelease`）一律只读它，不再各自从 `github.ref_name` 反推：
  - **标签触发**（`GITHUB_REF_TYPE=tag`）：标签名即发布标签，版本号取 `GITHUB_REF_NAME` 剥掉 `v`，再与 `wails.json` 比对，不等即拒绝发布。
  - **手动 dispatch**（`GITHUB_REF_TYPE=branch`）：此时 `github.ref_name` 是**分支名**，拿它当 `tag_name` 会朝 `main` 建 Release。
    故标签由版本号拼出（`v<version>`），`inputs.version` **留空即取 `wails.json`**、给了值只作「待核对的声明」——
    与内嵌版本不等即拒绝，**不接受它覆盖版本号**（否则等于发一份 `version` 高于盘上构件的清单）。
  - **已存在的标签必须指向本次构件所在的提交**：`git rev-list -n1 <tag>`（对注解标签会正确解引用到 commit）≢ `GITHUB_SHA` 即拒绝发布。
    典型现象是「定版后又推了修复 commit，却 dispatch 出包」——产物来自新提交，资产却挂在旧标签上。
- actionlint 已校验通过（T703）。


### 6.1 Linux runner 与工具链（三条工作流同一口径）

`ci.yml` / `lint.yml` / `release.yml` 的 Linux 作业一律 `ubuntu-24.04`，且 apt 装的是 **GTK4 一路**的开发头：

```
libgtk-4-dev libwebkitgtk-6.0-dev libsoup-3.0-dev libglib2.0-dev libx11-dev build-essential pkg-config
```

三个原因，都不是可调教的实现细节：

1. **Wails v3.0.0-beta.23 在 Linux 上走 GTK4**（全仓无 `-tags gtk3`），其 cgo 要求
   `pkg-config: gtk4 webkitgtk-6.0 libsoup-3.0 gio-unix-2.0 glib-2.0 gobject-2.0 + x11`。
   `ubuntu-22.04` 的 apt 源里**没有** `libwebkitgtk-6.0-dev`，装旧的 `libwebkit2gtk-4.1-dev` 编不过，
   于是 `go build ./...`、`go vet ./...`、以及 `go install github.com/wailsapp/wails/v3/cmd/wails3@…`
   （它自身要编译 `internal/operatingsystem/webkit_linux.go`，同一套 pkg-config 依赖）三处恒红。
   **顺序要求**：`release.yml` 的工具链步骤必须排在「Install Wails CLI」**之前**。
2. **actionlint 把 node20 运行时判为弃用（error）**，`workflow-lint` 作业因此恒红。现一律跟到跑
   node24 的主版本：`checkout@v5` · `setup-go@v6` · `setup-node@v6` · `pnpm/action-setup@v5` ·
   `upload-artifact@v7` · `download-artifact@v8` · `action-gh-release@v3`
   （`reviewdog/action-actionlint@v1` 是 docker 容器作业，不受该规则约束）。
3. **前端作业的 pnpm 主版本必须是 12**（`pnpm/action-setup` 的 `version: 12`，三条工作流同一值）：
   `frontend/pnpm-workspace.yaml` 只有 `allowBuilds:`（放行 `esbuild`／`vue-demi` 的安装期构建脚本）、
   **没有 `packages:`**，pnpm 9 读它即 `ERROR packages field missing or empty`，`pnpm -C frontend install
   --frozen-lockfile` 第一步退出码 1；pnpm 10+ 才允许该文件是纯配置。本机用 pnpm 12.4.1，
   `pnpm-lock.yaml` 的 `lockfileVersion: '9.0'` 由 pnpm 12 向后兼容读取，故 CI 跟本机而非相反
   （往工作区文件塞空 `packages:` 迁就旧主版本，等于让本机出包链路与 CI 分叉）。

> **`golangci-lint` 一步已真跑，且现已是阻断门禁**（原 `continue-on-error: true` 已删除）：原钉的 v1.61.0 用 go1.23 构建，
> 面对 `go 1.27` 目标直接 `can't load config …` 退出码 3，即**该步一项检查都没跑**（不是「跑过且干净」）。

### 6.2 三个互不同源的版本量（引用版本禁止凭印象）

一次发布同时存在**三条独立的版本取值链**，任何一条改动都不会自动传导到另两条：

| # | 版本量 | 唯一来源 | 落点 |
|---|--------|---------|------|
| 1 | 应用内自检版本（升级检查据此比对） | `Taskfile.yml` 的 `build` 任务：`-ldflags "-s -w -X phpo/internal/app.Version=$(bash scripts/version.sh)"`；`scripts/version.sh` 从 `wails.json` 的 `productVersion` 抽取 | 二进制内的 `internal/app.Version`（未注入时的静态默认值见该包） |
| 2 | deb / rpm 包版本 | `build/linux/nfpm.yaml` 的 `version:` 字段（**静态**，由 `scripts/bump-version.sh` 与 `wails.json` 同步维护） | 包元数据；文件名版本另由 `package:linux` 的 `mv` 用 `$(bash scripts/version.sh)` 拼出 |
| 3 | 发布清单 `manifest.json` 的 `version`、资产直链的 tag 与 `download_page` | `release.yml` 的 `Resolve version and tag` 步骤（id `ver`）：**基准取 `bash scripts/version.sh`**（= `wails.json` 的 `productVersion`），标签触发时校验 `GITHUB_REF_NAME` 剥 `v` 后与之一致，dispatch 时由版本号拼 `v<version>` | `steps.ver.outputs.version` / `.tag` ⇒ `gen-release-manifest.sh` 的 `VERSION` / `ASSET_BASE` / `DOWNLOAD_PAGE`，以及 `action-gh-release` 的 `tag_name` |

由此得两条硬规矩：

1. **推的标签必须逐字等于 `wails.json` 的 `productVersion`**（`v` + 该值，如 `v0.1.38` ↔ `0.1.38`）。否则第 3 条链会发出一份 `version` 高于盘上实际构件的清单——客户端据此升级到一个不存在的版本。
   **本条自 2026-09-24 起由 CI 阻断，不再靠人守**：`Resolve version and tag` 以 `wails.json` 为基准双向比对，
   标签/dispatch 参数与内嵌版本不等即 `::error::` + 退出码 1；同一道步骤还额外把住「已存在的标签指向别的提交」
   （`git rev-list -n1 <tag>` ≢ `GITHUB_SHA` 即拒绝），两类错配都会在签名与上传之前红掉。
2. **第 2 条链不会自动跟随定版**：`bump-version.sh` 只改 `wails.json` + `nfpm.yaml`，而第 1 条链是构建时现取，所以漏跑 bump 时会出现「二进制版本 ≠ 包版本」。核对方式（该次实跑的版本量为 `0.1.37`；三项同源的关系与具体数字无关，换版本后重跑即得当时的值）：

```
$ bash scripts/version.sh                  → 0.1.37   # 与 wails.json 的 productVersion 同源
$ grep -n '^version:' build/linux/nfpm.yaml → 6:version: 0.1.37
$ grep -n productVersion wails.json        → 12:    "productVersion": "0.1.37",
```

> **一处易被忽略的不对称**：Windows 产物名 `-DEXE_NAME=<ROOT_DIR>\build\bin\phpo-setup-x64.exe`（绝对路径，见 §6.5）**不带版本号**，而 Linux 侧 `package:linux` 会 `mv` 成 `phpo_<版本>_amd64.deb` / `phpo-<版本>.x86_64.rpm`。因此「从 Release 资产文件名反推版本」只对 Linux 成立；Windows 的版本只能看该 exe 的 `FileVersion` / 注册表 `DisplayVersion`（同源于 NSIS 的 `APP_VERSION`，见 §6.3）。

### 6.3 release run #1（tag `v0.1.37`）Windows 侧取证与修法

`https://github.com/xiaokentrl/phpo/actions/runs/35944238577` 判定 **failure**：`Build (linux)` 成功（artifact `pkg-linux` 24.6 MB），`Build (windows)` 与 `Build (darwin)` 均在第 10 步 `Package <os>` 失败，`Sign & Release` 因 `needs: build` 被跳过 ⇒ GitHub 上只有标签、没有 Release。

**Windows 的失败命令是逐字确证的**（用户登录态贴回的该步正文）：

```
Run wails3 task package:windows
  shell: C:\Program Files\Git\bin\bash.EXE --noprofile --norc -e -o pipefail {0}
  ERROR   task: Command "grep -oE '"productVersion"[^0-9]*[0-9][0-9.]*' wails.json | grep -oE '[0-9][0-9.]*'" failed: exit status 1
Error: Process completed with exit code 1.
```

即失败的是**定版前 `Taskfile.yml` 顶部那个全局 `vars.VERSION` 的 `sh:` 声明**，不是 `package:windows` 本身。三点机制要点（均已对 wails 自带的 task fork `github.com/wailsapp/task/v3@v3.40.1-patched3` 逐文件核实）：

1. **求值时机**：全局 `vars:` 在**编译期**无条件求值（`internal/compiler/compiler.go` 的 `TaskfileVars.Range`），发生在 `deps:` 之前 —— 所以 windows 该步**一行编译输出都没有**就退出，与 darwin 日志里 `task: [bindings] …` / `vite build` 正常跑完形成对照。
2. **执行器不是 cmd.exe**：是纯 Go 的 `mvdan.cc/sh/v3/interp`（`internal/execext/exec.go`），**没有**「Windows 默认 shell 会把单引号当字面量」这回事。**先前向用户汇报的「cmd 不识别单引号」根因判断有误，在此更正**；实测退出码是 `1`（管道末位 `grep` 无匹配）而非 `127`（可执行文件缺席），也说明命令确实跑起来了。
3. **两条看似可行的修法都不成立**：① CLI 传 `VERSION=x.y.z` 绕不过（`call.Vars` 在全局 vars **之后**才应用，求值照样发生）；② `${VERSION:-$(bash scripts/version.sh)}` 这类兜底不可用（`mvdan.cc/sh` 的 `expand/param.go` 对 `:-` 的默认词**非惰性**求值，等于把同一条管道留在原地）。

**采用的修法**：把版本从 task 的 `sh:` 里彻底移出，改由**进程环境变量**进入模板 —— `compiler.go` 用 `GetEnviron()` 把环境变量并入模板变量，因此 `{{.VERSION}}` 直接可读，且**不再有任何编译期求值**。三处改动：

| 文件 | 改动 |
|------|------|
| `Taskfile.yml` | 删除全局 `vars.VERSION`（原地留注说明为何不得再加）；`package:windows` 的 cmd **在本节不改**，仍 `-DAPP_VERSION={{.VERSION}}`，值改由环境提供（同一条 cmd 的路径宏形态在 §6.5 才改） |
| `.github/workflows/release.yml` | `Package <os>` 步骤（该步 `shell` 早已显式为 `bash`）改为：`export VERSION="$(bash scripts/version.sh)"` → 空值即 `::error::` + `exit 1` → `wails3 task package:<os>` |
| `build/windows/nsis/installer.nsi` | `APP_VERSION` 的 `!ifndef → "0.1.0"` 兜底换成两条 `!error`（未传入 / 空值）。**这条是修法的前提**：兜底值同时决定 `VIProductVersion`、`FileVersion`、注册表 `DisplayVersion`，安静落到 `0.1.0` 等于产出一份版本写错、且 §6.2 第 1 条链（二进制自检）与它对不上的安装包——比当前失败更坏 |

**验真（本机）**：`VERSION=9.9.9 wails3 task -dry package:windows` → `task: [package:windows] makensis -DAPP_NAME=phpo -DAPP_VERSION=9.9.9 …`、EXIT=0、`deps` 全列；`env -u VERSION` 同命令 → 该行为 `-DAPP_VERSION= `（空 ⇒ 由 NSIS 侧硬失败，不会产出假版本）。`actionlint .github/workflows/*.yml` EXIT=0。
> 该行是**当时**的渲染结果；§6.5 之后同一条命令的每个 `-D` 都带双引号、三条路径宏改成绝对路径，形态以 §6.5 的验真为准。

**如实登记的取证边界**：① **未在 windows runner 实跑**（本机无 windows、无 `makensis`，NSIS 预处理器的 `!error` / `!if "${X}" == ""` 未经真实编译）；② `build` 任务仍含 `$(bash scripts/version.sh)`，若 windows 上该调用取空，最坏后果是**二进制内**版本未覆盖（安装包版本由已守护的 `APP_VERSION` 决定，不受影响），此点同样未实测；③ 「管道末位 `grep` 为何无匹配」的确切原因未取回证据（`wails.json` 确在该 runner 的仓库根，且同一份 grep 在 linux/darwin 上成功）——修法刻意**不依赖**这一归因：那条求值已从链路上消失。
**darwin 当时按用户指示推迟**（「先修 windows，darwin 稍后再说」）：其失败与该全局变量无关，见下节 §6.4（本轮已修）。

### 6.5 Windows 链在 makensis 阶段的第二处必然失败（`.exe` 命名 + NSIS 目录基准）

§6.3 的修法只是让 `package:windows` **能开始执行**。它一旦真跑到 `makensis`，还会在两条与版本无关的缺陷上失败。两条判据均来自**读源码 + 本机实测**，不是从 run #1 日志推的——那次运行该行 0 秒即退出（§6.3），从未跑到 makensis。

#### 6.5.1 判据

| # | 缺陷 | 取证 |
|---|------|------|
| 1 | **产物名缺 `.exe`** | `build/windows/nsis/installer.nsi:82` 是 `File "${BUILD_DIR}\${BINARY_NAME}.exe"`（卸载段 line 111–112 同口径），即 makensis 必须找到 `build/bin/phpo.exe`。改前的 `build` 任务写的是 `-o build/bin/{{.BINARY}}`。实测（go1.27.1，最小 module）：`GOOS=windows go build -o out1/app .` → 落地文件名 **`out1/app`**；`GOOS=windows go build -o out2/ .` → **`out2/oprobe.exe`**。规则由此确定：`-o` 指向**显式文件名**时原样使用、**不追加** `.exe`；只有 `-o` 指向**目录**时才补。故 windows runner 上 `build` 产出 `build/bin/phpo` ⇒ `File not found`。 |
| 2 | **相对路径宏按脚本目录解析** | makensis 默认会把当前目录切到 `.nsi` 文件所在目录——官方文档对该开关的原文即 `/NOCD disables the current directory change to that of the .nsi file`（未传 `/NOCD` ⇒ 切目录是默认行为）。改前的命令从仓库根传 `-DBUILD_DIR=build/bin`、`-DICON=build/windows/icon.ico`，脚本内的 `File "${BUILD_DIR}\…"` 于是指向 `build/windows/nsis/build/bin/phpo.exe`；`OutFile "${EXE_NAME}"` 同样写不到 `build/bin`，下一步 `Upload staged artifacts` 便取不到分发物（该步 `path` 在 §6.6 前是 `build/bin/*`、现在是显式白名单，两种写法下结论相同：拿不到 `phpo-setup-x64.exe` 即 windows runner 上聚合零匹配 ⇒ `if-no-files-found: error`）。 |

#### 6.5.2 修法

| 文件 | 改动 | 为什么是这个形态 |
|------|------|------------------|
| `Taskfile.yml` 的 `build` | `-o build/bin/{{.BINARY}}{{exeExt}}` | `exeExt` 是 task fork 的模板函数（`internal/templater/funcs.go`：windows → `.exe`，其余平台 → 空串）。**Linux / darwin 渲染为空串**，产物名与改前逐字一致 ⇒ 已真机验证的 `package:linux`（`build/linux/nfpm.yaml` 的 `src: build/bin/phpo`）与 `package:darwin`（`cp "build/bin/phpo"`）均不受影响。另一条路（改 `installer.nsi` 的 `File` 行去匹配无后缀名）会把缺陷留在原地——Windows 上无 `.exe` 的可执行文件本就是异常形态。 |
| `Taskfile.yml` 的 `package:windows` | 三条路径宏（`EXE_NAME` / `BUILD_DIR` / `ICON`）与脚本参数一律改成 `{{joinPath .ROOT_DIR …}}`，且**每个参数整体加双引号** | `joinPath` 即 `filepath.Join`（宿主原生分隔符），`.ROOT_DIR` 是 task 的 `getSpecialVars` 提供的根 Taskfile 绝对目录（windows runner 上形如 `C:\a\phpo\phpo`）。双引号不可省：反斜杠在裸参数里会被 shell 当转义字符吃掉（task 的执行器是纯 Go 的 `mvdan.cc/sh`，见 §6.3）。**绝对路径同时让第 2 项的相对基准语义变成无关问题**——与 §6.3「修法刻意不依赖归因」同一策略。 |
| `build/windows/nsis/installer.nsi` | **不改** | 收到绝对路径宏后，脚本内的相对基准不再参与正确性；改它等于对「`File` 的相对路径究竟按哪个目录解析」这一未实测语义下注。两条 `!error`（`APP_VERSION` 未传入 / 空值）保持 §6.3 原状。 |

**顺带收口一处口径错误**：该任务的 `desc` 此前暗示可在本机跑 `package:windows`。本机无 `makensis`，且 `build` 现在明确产 `.exe`，故 `desc` 改为「需在 windows runner 执行，且环境里要有 VERSION」——与 `package:darwin` 同口径。

#### 6.5.3 验真（本机，Linux）

`VERSION=9.9.9 wails3 task -dry package:windows` → EXIT=0，依赖链 `[bindings] → [frontend:build] → [build] → package:windows`，末两行渲染逐字为：

#### 6.5.5 当时登记的开放问题（**已收口，见 §6.6**；本条保留原判据并更正其中两处错误）

原判据：`Upload staged artifacts` 的 `path: build/bin/*` 会把 `go build` 留在原地的**裸可执行文件**（Linux 的 `phpo`、darwin 的 `phpo`、windows 修后的 `phpo.exe`）一并装进 `pkg-<target>`；`release` 作业三个 `download-artifact` 以 `merge-multiple: true` 平铺进 `out`，`files: out/*` 因此会把裸二进制当成 GitHub Release 资产发布。**这一条至今成立**，且是本节改动的直接动因。

**但同一句里对下游两个脚本的断言有两处错误，实测（`BIN_DIR=/tmp/relsim/out`，伪造三平台产物名 + 真私钥签名）已否证**：

| # | 原表述 | 实测结论 |
|---|--------|----------|
| ① | 「`gen-checksums.sh` 还会把它写进 `checksums.txt`」 | **只对 windows 成立**。该脚本的 `ARTIFACT_RE='\.(exe\|dmg\|AppImage\|deb\|rpm\|pkg\.tar\.zst\|tar\.gz)$'` 含 `\.exe$`，故 `phpo.exe` 确实进清单（实测 5 项含 `phpo.exe`）；而 Linux/darwin 的裸 `phpo` **无扩展名，不进清单**。正确表述是「windows 的裸二进制连 `checksums.txt` 都会进」。 |
| ② | 「`gen-release-manifest.sh` 按扩展名识别、不会为它生成条目」 | **错误**。该脚本的 `case` 有 `*.exe) os=windows; format=exe`，`phpo.exe` **会被认成一颗合法的 windows/exe 升级资产**。实测清单里同时出现 `phpo.exe` 与 `phpo-setup-x64.exe` 两颗 `os=windows,format=exe`（`signed=5`），而 `resolvePlatform`（`internal/updater/source.go`）按 assets 顺序取**第一颗**命中本机平台的条目 ⇒ windows 客户端有一半概率去下载一个不是安装器的裸可执行文件。这比「多传一个无用资产」严重，是**发布链上的真实缺陷**；同脚本原本的去重逻辑只 `echo` 警告、**没有 `continue`**，等于没去重。 |

§6.4 的 `package:darwin` 收尾那条 `rm -rf build/bin/phpo.app` 只挡住了目录，挡不住裸二进制这一条。

### 6.6 发布资产集合收口：upload 白名单 + 清单真去重 + 定序（2026-09-24）

同一目录被四处按不同口径解读（`upload-artifact` 的 glob、`action-gh-release` 的 `files: out/*`、`gen-checksums.sh` 的 `ARTIFACT_RE`、`gen-release-manifest.sh` 的扩展名 `case`），修法不是在四处各打补丁，而是**把它压成三层防线**：产物根本不出仓（第 1 层）→ 万一出仓，同平台只留一份（第 2 层）→ 留哪一份由固定顺序决定而非 locale 决定（第 3 层）。

| 层 | 文件 / 改动 | 判据与理由 |
|----|-------------|-----------|
| 1 | `.github/workflows/release.yml` 的 `Upload staged artifacts`：`path: build/bin/*` → 四行显式白名单 `build/bin/*.deb` / `*.rpm` / `*.dmg` / **`build/bin/phpo-setup-x64.exe`** | **白名单而非 `*.exe`**：§6.5 判据 1 修好后 windows 的裸二进制**正是** `phpo.exe`，`*.exe` 会把它放行到与安装包同一个 `(os, format)` 键上。**allowlist 与 denylist 的失效方向不同**——分发物改名时该 runner 上聚合零匹配 → `if-no-files-found: error` 响亮失败；denylist 在裸二进制改名时静默漏网。AGENTS.md §11.1 的分发物清单里也没有裸二进制。 |
| 1b | 同上：确认多行 glob 的报错语义 | `actions/upload-artifact` v7 README 原文（line 243）：**"If a path (or paths), result in no files being found for the artifact, the action will succeed but print out a warning."** 即 `if-no-files-found: error` 作用于**聚合结果**，不逐 pattern 报错——各 runner 上不匹配的另外三行是常态，不会因此失败。该原文经 `api.github.com/repos/actions/upload-artifact/readme`（`Accept: application/vnd.github.raw`）取得（本机对 `raw.githubusercontent.com` 直连被拒）。 |
| 2 | `scripts/gen-release-manifest.sh`：去重从「只 `echo` 警告」改为 `continue 2` **真正跳过**，且**移到签名校验之后** | 客户端 `resolvePlatform` 取第一颗命中项 ⇒ 同平台两份资产等于让它赌顺序。**判重在签名之后**是必需的：未签名的那一份本来就不进清单，若先登记 `seen` 会把同平台唯一那份**已签名**的包挡掉（`phpo.exe` 未签而 `phpo-setup-x64.exe` 已签的场景即此）。 |
| 3 | 同脚本：遍历从 `find … \| sort` 改为 `find … \| LC_ALL=C sort` | 「先出现的一份」不得取决于 runner 的 locale。本机实测（同目录 `ls -1 *.exe \| sort`）：默认 `LANG=zh_CN.UTF-8` 下 **`phpo.exe` 在前**（安装器反而落选）；`LC_ALL=C` 下 `phpo-setup-x64.exe` 在前（`-` = 0x2D < `.` = 0x2E）。钉成 C 序后即使第 1 层被绕过，保留下来的仍是安装包。 |
| — | `Taskfile.yml` 两处注释：`package:windows` 的「下游 upload-artifact 取 `build/bin/*`」、`package:darwin` 收尾的「`build/bin/*` 会整体进 upload-artifact」 | 因第 1 层改动而失真的**本轮自身产物**，按 §3.4.3「本次修改产生的过时内容可直接修正」处理；不是顺手优化相邻注释。 |

**验真（本机，Linux）**：

- 第 2/3 层：`/tmp/relsim/out` 伪造三平台六个产物名（含裸 `phpo` 与 `phpo.exe`），用仓库外真私钥 `sign-release.sh sign` 出 `.sig` 后跑 `VERSION=9.9.9 BIN_DIR=… scripts/gen-release-manifest.sh` → stderr 一行 `! 同一平台已有一份签名包，本条跳过（重复: windows/exe → phpo.exe）`，`signed=4`，清单里 windows/exe **只剩 `phpo-setup-x64.exe`** 一颗（改前实测是 5 颗、两颗 windows/exe）。
- 排序对照：默认 locale 与 `LC_ALL=C` 下 `*.exe` 的先后**确实相反**（见上表第 3 行）。
- `BIN_DIR=/tmp/relsim/out scripts/gen-checksums.sh` → 5 项、含 `phpo.exe`，即 §6.5.5 表 ① 的实测依据。

**取证时效**：`cleanup-actions.yml`（`keep: 1`，下次 **2026-09-27 00:00 UTC**）会清掉超窗 run，故本轮全部判据（逐步 `conclusion`、三份产物字节数与 digest、两条 `Error` 原文）已当轮抄进本节。
