# 应用升级

> 对应 AGENTS.md §1.10 / §5.9 / §0.2-18 / §3.3 硬红线 6 / 工单 T704。phpo 自身支持版本检查与自动升级；升级包**必须** SHA256 + 签名双校验。冲突以 AGENTS.md 为准。

## 1. 检查频率（§0.3 / §5.9）

- **启动时 + 每 24 小时 + 用户手动**。
- 实现：`internal/updater/scheduler.go` `DefaultInterval = 24h`，`Start(ctx)` 立即 `runOnce` 再 `time.NewTicker`；网络不可达仅告警，不影响使用（最小限制，§0.2-16）。

## 2. 发布源与清单（`updater/checker.go` / `updater/source.go`）

`Release` JSON：`{ version, changelog, download_page, size, url, sha256, signature, assets[] }`。

- 顶层 `url/sha256/signature/size` 是**旧式单包清单**的形态，也是「本次要装的那一颗」的最终落点。
- `assets[]` 每项 `{ os, format, url, size, sha256, signature }`：多平台各一份，`os` 用 `runtime.GOOS` 同词表（`linux` / `windows` / `darwin`），`format` 仅 linux 有意义（`deb` / `rpm` / `appimage`）。
- `download_page`（`omitempty`）是发布页地址，供界面「打开下载页」按钮；清单不写即无该按钮。
- `HTTPSource.FetchLatest`：拉取发布清单（`encoding/json`，1 MiB 上限）。
- `IsNewer(latest, current)`：`pkg/version/semver` 比较先后。
- `Checker.Check(ctx)` → `(*Release, bool 有新版本, error)`；发现新版发射 `update:available { version, changelog, size, source, download_page }`（`source` 即命中该清单的发布源名，由 `Sources` 回填，**不是**清单字段）。

### 2.1 多源并发探测与 15 秒独立超时（`updater/source.go`）

源清单来自 `config.yaml` 的 `update_sources`（数组，用户可增删）；匿名读取，不存任何凭据（§1.5）。

```
Sources.FetchLatest(ctx):
  全部源并发 fetchOne —— 每源独立 context.WithTimeout(SourceTimeout = 15s)，互不等待
    成功 → rel.Source = src.Name（源名回填在 fetchOne 内）
    失败 → 记下 "源名: 原因"
  在成功的源里取 version 序最新的一份；版本并列取数组顺序靠前的一条
  全部失败 → 「所有发布源均不可用（github: …；gitee: …）」（逐源点名，顺序 = 数组顺序）
```

- **为什么不是「按序命中即返」**：镜像源常滞后于原始发布（gitee 尚未同步 GitHub 的最新版），命中即返等于把需求里的「自动检测最后发布的版本」做成「第一个可用源宣称的版本」。现语义是**跨源取版本最大**，数组顺序的残留语义只有两条：并列版本的裁决次序、全败时逐项点名的次序。
- **代价与收益要一起看**：并发探测等于每次检查都拨全部源（N 条匿名 HTTP GET），且整次耗时上界是**最慢那一源**的 15 秒；换来的是全败场景从「N × 15s 串行累加」压回 ≈15s（用例 `TestSources_TimeoutsDoNotStack` 锁死不叠加）。
- 未配置 `update_sources` 即回落到 `config.DefaultUpdateSources()`（GitHub Releases）；桥接在 `internal/app/di.go` 的 `loadUpdateSources()`（`internal/config` 不反向依赖 `internal/updater`，§0.2-12）。
- 中国用户 / 国外用户各自更想先连哪一份，由用户在 `config.yaml` 里调整数组顺序决定（并列版本时靠前者优先），并**不做地区自动判定**（应用无可靠的语言/地区信号，且自动改源等于替程序员做决定，§0.2-15）。
- 命中后按本机平台选包：`resolvePlatform` 先严格匹配 `os`+`format`（linux 上按 `/etc/debian_version` 判 `deb`/`rpm`），再放宽到仅匹配 `os`；`assets` 缺席即旧式单包清单，顶层字段原样可用。选出后写回顶层 `URL/Size/SHA256/Signature`，因此下载、双校验、安装三步读的是同一组字段。

### 2.2 发布清单契约的一次真跑通（2026-09-24 取证）

清单由 `scripts/gen-release-manifest.sh`（shell）产出、由 `internal/updater`（Go）消费，两侧键名一旦漂移即表现为「清单内无本机平台」，故用一次性取证把这条跨语言契约走通一遍（临时私钥与假产物只在 `/tmp`，未落仓库）：

```
scripts/sign-release.sh genkey ./rel.pem                        # 真 Ed25519 密钥
scripts/sign-release.sh sign ./rel.pem out/<每个产物>            # 5 份 .sig
VERSION=0.1.40 ASSET_BASE=… DOWNLOAD_PAGE=… CHANGELOG=… \
  bash scripts/gen-release-manifest.sh                          # → out/manifest.json（签名包 5 份）
```

产物经本地 HTTP 服务喂给 `HTTPSource` → `Sources.FetchLatest` → `resolvePlatform`，逐项实测：

| 断言 | 结果 |
|------|------|
| 五个平台各自选包 | `windows/exe`→`phpo-setup-x64.exe`、`darwin/dmg`→`phpo-x64.dmg`、`linux/deb`→`phpo_0.1.40_amd64.deb`、`linux/rpm`→`phpo-0.1.40.x86_64.rpm`、`linux/appimage`→`phpo-x86_64.AppImage`，`URL/Size/SHA256/Signature` 与清单逐字段一致 |
| 每颗包的 `VerifyPackage` | 全过（SHA256 + Ed25519，公钥即 `sign-release.sh pubkey` 导出串）——脚本的签名约定与 `verifier.go` 一致 |
| `Checker.Check` 的事件载荷 | `{"version":"0.1.40","changelog":"…","size":900000,"source":"gitee","download_page":"https://github.com/xiaokentrl/phpo/releases/tag/v0.1.40"}`：`size` 是**本机那颗包**的体积（不是清单里第一颗），`source` 由 `Sources` 回填，内部字段 `assets` 不外泄 |
| 逐源切换 | 首源 404 → 换次源成功且 `Source` 为次源名；两源全失败 → 错误消息逐个点名；单源挂起 → 独立超时后切换（`SourceTimeout` 仍为 15s，超时值在取证里被收紧到毫秒级以覆盖分支） |
| 负面形状 | 无 `assets` 的旧式清单原样可用；`os` 不在清单内 → 报「清单内无本机平台（plan9）」而非静默装错包；产物改一字节 → `ErrChecksum`；签名尾部加字符 → `ErrSignature`；公钥为 `nil`（占位未替换）→ `ErrNoPublicKey` 拒装 |

配套结论：`scripts/gen-checksums.sh` 的 `ARTIFACT_RE` 只收安装包扩展名，`manifest.json` 与 `.sig` 均被排除，因此 `release.yml` 里「先 checksums 后 manifest」的顺序不会让清单漏进 `checksums.txt`，不是缺陷。

> **本轮之后的语义变更（同一日）**：上表的「逐源切换」一行是在「按序命中即返」的实现对上取的证。`FetchLatest` 随后改为**并发探测 + 跨源取版本最大**（§2.1），该行的三个现象在新实现下结论不变（恰好一源成功即取它、全败逐源点名、挂起源被独立超时排除），但**多源同时成功时取版本最高的一份**这一格是新增判据，由常驻用例 `TestSources_PicksNewestAcrossSources` / `TestSources_EqualVersionKeepsConfigOrder` / `TestSources_TimeoutsDoNotStack` 锁死，不再依赖一次性取证。

> 本次取证用的临时用例（`internal/updater/manifest_probe_test.go`）依赖 `/tmp` 下的假产物，留在仓库会永远走 skip 分支成为死码，故跑通后删除；上表是其唯一留痕。契约的常驻回归由 `internal/updater/source_test.go`（Go 侧解析/选包）承担。

## 3. 双校验（硬红线 6，供应链安全）

`internal/updater/verifier.go`（约定签名 = `base64(Ed25519(lowercase-sha256-hex 字符串))`，被签消息为 SHA256 十六进制小写串本身，非文件字节）：

```
VerifyPackage(path, wantSHA, pub, sigB64):
  pub == nil → ErrNoPublicKey（无公钥拒绝一切升级）
  got = SHA256File(path)
  VerifyChecksum(got, wantSHA) → 不符 ErrChecksum
  VerifySignature(pub, got, sigB64) → ed25519.Verify(pub, lower(got), sig) → 不符 ErrSignature
```

- 公钥来源：`updater/embed.go` `//go:embed signing/public.key`，`base64.StdEncoding` 解码为 32 字节 Ed25519 公钥；长度不符 → `nil` → 拒绝。
- 公钥与私钥：私钥仅存发布机（`.gitignore` 屏蔽 `*.key`/`*.pem`）；公钥唯一入库路径为 `internal/updater/signing/public.key`（不再有 `build/signing/`）。生成/签名流程见 `docs/打包发布.md`。

## 4. 升级流程（三段式，`UpdateApply`）

```
App.UpdateApply → task.Manager（串行 FIFO；前面有任务则排队，同标签重复提交回 ErrQueued）
  stage=download : downloader.go 流式下载 + 进度(update:progress) + 原子落盘
  stage=verify   : VerifyPackage（SHA256 + Ed25519 双校验，失败中止→回滚）
  stage=install  : installer_{windows,darwin,linux}.go 安装 + 写 marker
  成功 → emit update:done { status:success, version }
  失败 → rollback.go（清 marker）→ 下次启动自动回滚旧版本 → update:done { status:failed }
```

- 安装方式随平台（§8）：Windows NSIS 静默 / macOS .app 替换 / Linux AppImage 替换；装哪一颗由 §2.1 的 `resolvePlatform` 按本机 `os`+`format` 选出。
- 回滚（`updater/rollback.go`）：崩溃/失败标记 + 下次启动自动回到旧版本（可恢复性，§5.13.1）。
- **已登记的落差（未修）**：`installer_linux.go` 按 AppImage 语义执行 `pkgPath --update`，而 `task package:linux` 当前只产出 deb/rpm——Linux 自身升级在这套产物形态下走不通（与多源改造无关，需先裁决 §8 的 Linux 安装方式）。

## 5. 前端接线

- `useUpdater.ts` + `updaterStore.ts`：订阅 `update:available/progress/done`（`update_sources` 与命中源名随 `update:available` 的 `source` 回流，不进快照）。
- **三种处置**（`UpdateModal.vue`，对应 `update.dismiss` / `update.page` / `update.background`）：
  | 处置 | 行为 |
  |------|------|
  | 忽略此版本 | `updaterStore.dismiss(version)` 写 `localStorage`（键 `phpo-update-dismissed`）——UI 偏好（§3.1 原则 5），**不落 `config.yaml`、不落库、不新增事件名、不改后端状态**；该版本即不再触发徽标 |
  | 打开下载页 | `Browser.OpenURL(download_page)`（真实宿主）；`download_page` 缺席即不渲染该按钮，demo 通道只 toast |
  | 后台下载 | `UpdateApply` 走三段式任务，弹窗**提交即关闭**，进度由左上角徽标 + 弹窗内进度条承载（等待期不挂瞬时弹窗，§5.16.2 同口径） |
- `UpdateBadge.vue`（`App.vue` 的 `.app-brand` 之下，左上角）：一句话给出「更新中心 - N 项可用更新，更新源 X」/「下载中 N%」/「升级完成，待重启」/「升级失败」，点击回到升级弹窗。状态只取 `updaterStore`（后端权威），样式写在组件的 scoped 块，**不改 `base.css` 与冻结原型 SSOT**（§5.6.4 同先例）。后端每次只报一个最新可用版本，故计数恒为 1。
- 进度条：`update:progress` 的 stage/percent/speed（连续量，不进抽屉日志流水，§5.6.2）。`stage` 只有 `download` / `verify` / `install` 三个取值，与 `update.stage.*` 三把文案键一一对应（`api/mockEvents.ts` 的 DEV 载荷同此，不得写 `downloading` 这类第三种取值——它渲染不出人话）。
- `api/updater.ts` 的 `checkUpdate()` **整体透出**后端 DTO（`source` / `download_page` 一并返回，不逐字段重撷）：徽标的「更新源」与「打开下载页」入口因此不再只依赖 `update:available` 到达的先后。
- 不做乐观更新：升级结果同样只来自事件（硬红线 4）——但**新一轮的 `update:available` 必须清掉上一次升级的终态**（`updaterStore.setAvailable` 里 `done = null`）。否则升级失败后再点「检查更新」，后端发了新版本、徽标却仍顶着「升级失败」，需求里那句「更新中心 - 1 项可用更新，更新源 X」永远出不来；`progress` 不清（标签判定里 `busy` 先于可用版本），下载期不会被一次并发检查打断。

### 5.1 徽标四态与三选项的浏览器走查（2026-09-24 取证）

驱动方式只有一个可行解：`npx vite --port 5199`（**DEV 服务器**）+ 页面内 `__phpoMock.emit(...)`。事件泵 `api/mockEvents.ts` 在 `App.vue` 里是 `if (import.meta.env.DEV) await import(...)` 才加载的，**构建产物不含它**——所以拿 `pnpm build` 的 `dist` 起静态服务无法驱动 `update:*`，这也是此前该链路只经 `vue-tsc` 与静态走查的原因。

| 序列（demo 通道，全程控制台零 error） | 实测徽标 |
|------|------|
| `update:available`（`source: 'gitee'` + `download_page`） | `更新中心 - 1 项可用更新，更新源 gitee`，类 `upd-badge-avail`，几何位置 `x=12 / y=46`（侧栏 `.app-brand` 之下即左上角）；同帧 toast「发现新版本 0.1.40」 |
| `update:progress` `{stage:'download',percent:55}` | `下载中 55%` |
| `update:done` `success` / `failed` | `升级完成，待重启`（`-ok`）/ `升级失败`（`-err`） |
| 失败之后再发一个更高版本的 `update:available` | **回到** `更新中心 - 1 项可用更新，更新源 gitee`（即上一条规则的判据；未修前此格停留在「升级失败」） |
| 点徽标 → 弹窗 | 行「当前版本 / 新版本 0.1.42 / 安装包体积 43.9 MB / **更新源 gitee**」+ changelog + SHA256·Ed25519 提示；按钮四颗：`检查更新` `忽略此版本` `打开下载页` `后台下载` |
| 点「忽略此版本」 | 徽标消失、弹窗关闭、`localStorage['phpo-update-dismissed']='0.1.42'`；**再发同版本 `update:available` 仍不出徽标**，发 `0.1.43` 即重新出现 |
| `update:available` 不带 `download_page`（源名 `custom-mirror`） | 按钮只剩三颗（`打开下载页` 不渲染），徽标把源名原样透出：`更新中心 - 1 项可用更新，更新源 custom-mirror` |

**仍未覆盖**：真实宿主的点击级验收（原生窗口 + 真 `Browser.OpenURL` + 真 `UpdateApply` 链路）——**真宿主 GUI 未走查**；本轮取证是 demo 通道下的组件级走查。
- 检查失败（断网）：提示「无法检查更新。不影响使用。」（§5.7 doctor 文案）。


## 6. 禁止清单（§0.2-18）

- ❌ 跳过 SHA256 或签名任一环节。
- ❌ 公钥缺失时放行升级（必须 `ErrNoPublicKey` 拒绝）。
- ❌ 校验非降级的强制自动升级（用户可手动/关自动）。
