# 端口策略

> 对应 AGENTS.md §1.9 / §5.8 / §0.3 / 工单 T704。三档行为：**新建站点端口占用只告警 + 站点降级（不顺延、不阻断）**，**改已有站点的端口才顺延（不报错）**，**服务端口占用报错**。冲突以 AGENTS.md 为准。

## 1. 端口行为对照

| 维度 | 新建站点端口 | 改已有站点端口 | 服务端口 |
|------|------------|--------------|---------|
| 默认值 | 80（§0.3） | 站点当前端口 | 各服务标准端口（SVC_META / `versions` 建议） |
| 占用行为 | **不改用户所填端口**：告警 + 站点降级（vhost 暂不落盘、端口暂不发布） | **顺延 [1,65535] 内首个可用，不报错** | **报 `portInUse`，不顺延** |
| 是否阻断 | 否，站点照常创建 | 否 | 是 |
| 用户指定 | 允许任意 1–65535 | 允许任意 1–65535 | 允许任意 1–65535 |
| 落点 | 降级态仅落库 + 站点目录 + hosts；空闲时写 vhost `listen` 并发布端口 | vhost `listen` | 容器端口发布 / 配置 |
| 生效时机 | 写 vhost + `nginx -t` + reload 即生效 | 同左 | **只在建容器时落定**：改端口仅写 `config.yaml`，`Start`/`Stop` 改不动已建容器，必须重建（`Reinstall`）才发布新端口 |
| 自愈 | 腾出该端口后 `SwitchPHP` / `SetPort` / `SetRewrite` 任一次即补写 vhost 并发布端口 | — | 重建前预检端口占用，冲突即拒绝且不碰正在跑的容器；腾出端口后重建即生效 |

## 2. 权威值（§0.3）

- 可用端口范围：**1–65535**（`MinSupported=1`，`MaxSupported=65535`）。
- 站点默认端口：**80**（`DefaultPort`）。
- 新建站点端口冲突：**不顺延**——保留用户所填端口，只回传占用信息，由上层弹框告警 + 站点降级。
- 改站点端口顺延范围：**1–65535 首个可用**，无窗口上限、耗尽不报错。
- 服务端口冲突：报 `portInUse`（`errs.PortInUse`）；不自动顺延。
- 服务端口改动：**不即时生效**——写入 `config.yaml` 后需重建容器（`LifecycleService.Reinstall`）才落到端口发布上；重建在 Pre-Clean 之前做占用预检，冲突则整个操作拒绝、已运行容器原样保留。
- 占用判定唯一来源：`store.CollectUsedPorts(snap, excludeDomains)`（mysql/pgsql/redis 服务端口 + 既有站点端口，先到先得），**不做真实 TCP 探测**。

## 3. 实现（`pkg/port` + `internal/preflight`）

- `Validate(raw, used, Options)`：格式（纯数字、≤5 位）→ 范围（1–65535）→ 排除（`Exclude`，编辑站点自身端口视为空闲）→ 占用判定。三种互斥档位：
  - `Options.KeepOnConflict=true`（**新建站点**）：占用则端口原样返回 `Result{Ok:true, Value, Occupied:true, Msg}`，**不改端口**。
  - `Options.AutoAdvance=true`（**改站点端口**）：占用则 `FindNextAvailable(desired, MaxSupported, MinSupported, used)`（向上优先，再回绕）返回 `Result{Ok, Value, Adjusted:true, Original}`；文案 `errs.PortAdvance`（"端口 {from} 已被占用，自动顺延至 {to}"）。
  - 两者皆 `false`（**服务端口**）：占用直接 `errs.PortInUse`，不顺延。
- `internal/preflight/validators.go`：`portConflict` 枚举 `conflictKeepWarn` / `conflictAdvance` / `conflictBlock` 一一对应上述三档，`validatePort` 据此装配 `Options`。
- `sequence.go#FindNextAvailable`：全范围扫描首个可用，**无窗口上限**（§1.9：去除「耗尽报错」）。
- `probe.go#Probe/Available`：真实 listen 探测，仅备用；站点/服务端口占用一律以账本（`CollectUsedPorts`）为准。

## 4. 落地链路

- 新建站点：`SiteAdd` → preflight `site-add` 先过唯一服务门禁（**Nginx 未安装 = 阻断**，无 nginx 无法发布站点；已装未运行只降级），再以 `conflictKeepWarn` 校验端口 → 占用则 `r.warnf` 降级告警（前端 `usePreflight` 同文案 → `DangerConfirm` 弹框）→ `SiteService.serveReady`（纯函数 `siteServeReady`）判定「**Nginx 已装且在运行** + 所选 PHP 已装 + 所选端口未被占用」：
  - 就绪：创建站点目录 → 写 vhost（`nginx -t` 必过，硬红线 2）→ 写 hosts → 发布端口 → 落库并广播 `state:changed`，前端 `addSite` 返回后立即 `syncState()` 拉权威快照刷新列表。
  - 降级：跳过写 vhost 与发布端口，站点目录 / hosts / 落库照常，**端口原样保留**。nginx 已装但未运行同样走这条降级路（门禁只卡「未安装」）。
- 自愈（补齐降级站点，`SiteService.ReconcileServe`：逐站点重判就绪、**补写缺失的 vhost**、reload、按发布集重发布端口并广播）：
  - 服务事件后挂「补齐站点 vhost」步骤（`AppService.healStep`，判定函数 `siteHealedBy(kind, op)`）：**nginx 装 / 重建 / 启动**（写 vhost 要的 `nginx -t` 只能在运行中的容器里跑）、**php 装 / 重建**（缺上游而降级的站点有了 fastcgi 目标）、**mysql / pgsql / redis 卸载**（让出被占端口，卡在端口占用的站点可发布）。php 卸载、nginx 停止只会让站点更降级，补齐必然空转，故不挂。补齐失败只记任务日志不判整个安装任务失败（容器已按请求装好/卸掉，站点仍可在下次就绪事件自愈）。
  - 站点写操作让出的端口同样要补齐别的站点：`Remove`（删站）与 `writeVHost`（改端口等）在 **Apply 段末尾**走 `healFreed`——步骤阶段库里仍是旧占用表，那时补齐会照旧判定「端口被占」而空跑；补齐失败只记一行 `task:log` 不上抛（本次操作已成功，回滚整任务与本意相反）。
- **编辑站点的门禁与建站不同**：`site-port` / `site-vhost` / `php-switch` / `rewrite` 四个动作在 preflight 过「站点存在」后再过 `nginxServing()`——**Nginx 未安装报 `nginxNeeded`，已装未运行报 `errs.NotRunning: Nginx（vhost 改动须经运行中的 Nginx 校验后才能落盘，请先启动 Nginx 再重试）`**，均阻断（前端 `usePreflight` 同文案）。理由：建站没有旧 conf，未运行只降级即可；编辑必须把新正文写盘，而写盘前的 `nginx -t`（硬红线 2）只能在运行中的容器里执行，容器停了这条链必然失败。这里不降级还有一层：`ReconcileServe` 只补**缺失**的 vhost（`os.Stat` 到盘上已有即跳过），若放行编辑、跳过写盘，盘上就会长期留着一份与库内状态不一致的旧 conf，再没有自愈入口。
- 发布集（`SiteService.publishPorts`）只计入 **vhost 已落盘**的站点端口，并剔除数据服务（mysql/pgsql/redis）已占用的端口：降级站点库里仍记着端口，若被后续任一次重发布带给 nginx，容器会去抢绑一个没人服务（甚至已被占用）的宿主端口而绑不上，届时全站瘫痪。
- **重发布（`LifecycleService.RepublishNginx`）有两道闸，都在动容器之前**：
  - **未运行即整体跳过**（`engine.Client.ContainerRunning` 按 Docker 实际态判，不看库里的 running 标记）：用户主动停掉（或手工删掉）nginx 后，站点写链路不得把它悄悄拉起并占回宿主端口——那等于替用户决定「nginx 该在跑」。停机期间站点维持降级，端口等 nginx 下次启动的就绪补齐再绑（`siteServeReady` 要求「已装 **且在运行**」，界面本就把它显示为降级，两侧口径一致）。
  - **发布集与容器当前绑定一致即不重建**（`sameHostPorts` 比对 `engine.PublishedPorts` 实读值与目标 `spec.PortMap`）：重建等于把整站白闪断一次，而端口校对会被就绪补齐链路反复触发，无差异时必须不动手。
- 就绪入口（`ReconcileServe`）除补 vhost 外**每次都用权威发布集校对一次宿主端口**：停机期间的站点写操作可能压根没发布成功，容器绑的端口集已与站点不符（例如停 nginx 时删了站点，重启后 nginx 仍占着已删站点的宿主端口）。站点写链路自身的 `healFreed` 走 `checkPorts=false`——它已在步骤里按当轮并集发布过，只有真补齐了别的站点 vhost 才再发一次，避免同一次操作把 nginx 重建两遍。
- 改站点端口：`SiteSetPort` → preflight `site-port` 先过 `nginxServing()`（见上）再以 `conflictAdvance` 顺延（排除自身域名与当前端口）→ UI `usePortSuggest` 展示「80→81 已调整」（等后端回流，不乐观，硬红线 4）。
- 装服务 / 改服务配置：服务端口占用报错，用户自行改端口后重试。
- 安装期端口：安装弹窗填的端口随 `Install(ctx, kind, version, opts)` 一次带过（后端先跑 `install` 裁决，占用即 `portInUse` 且**不落任何配置**，通过后才写 `config.yaml` 再建容器）。**不能改成「先 `SetServicePort` 再安装」**——`update-config` 要求版本已安装，未装态会被 `notInstalled` 拦下，等于任何带端口的服务都装不起来（对应原型 `applyStateChange` 的 `type==='install'` 分支）。
- 改服务端口后生效：`EnvService.SetPort` 只落 `config.yaml`（回显立即变、运行态不变）；`ServiceView` 的行内端口保存后提示「端口已写入 config.yaml…点「重建生效」后才会真正切换」（`svc.portPending`）。凡有宿主端口发布的服务（mysql/pgsql/redis/**nginx**）卡片都提供「重建生效」按钮 → preflight `update-config`（field=port，复用同一占用裁决，不新增 action）→ `AppService.Reinstall` → `LifecycleService.Reinstall`：`assertHostPortsFree` 以 `store.CollectUsedPorts` 判占用（含注册表默认端口补档），冲突在 Pre-Clean **之前**返回 `portInUse`；通过则走与安装同一条幂等管道（Pre-Clean 同名容器 → create（新端口发布）→ start → Post-Verify），数据卷与宿主目录不动。nginx 的基准端口（`NGINX_{VER}_PORT`）与站点端口并集一起发布，同属「只在建容器时落定」这一类，故同样需要重建才生效。
- 特权端口（80）：Windows 免特权直绑；mac/linux 需 root/setcap，不可绑时由用户换端口（新建站点不再自动顺延）。

## 5. 明确不做

- ❌ 把站点端口硬编码为 80（默认 80，用户可填任意端口，§0.2-17）。
- ❌ 新建站点擅自改动用户所填端口（占用只告警 + 降级，不顺延，§5.8）。
- ❌ 因端口占用阻止建站（最小限制原则：能警告的不要阻止）。
- ❌ 站点端口耗尽时报错（改站点端口顺延无窗口上限，理论上总有可用位）。
- ❌ 服务端口自动顺延（会与已运行服务冲突而不自知）。
- ❌ 把改服务端口当成即时生效（Docker 端口发布只在建容器时确定；不重建却显示「已生效」属失真状态）。
- ❌ 为了应用新端口先删容器再判占用（端口绑不上等于白丢一个在跑的服务；预检必须在 Pre-Clean 之前）。
- ❌ 限制端口范围（1–65535 全开，§0.2-15）。
